# 0.3.4 部署与真机验收清单：跨设备删除同步

> 方案与理由见 `0.3.4-cross-device-delete-sync.md`。
> 一句话背景：以前 **A 删掉一条记录，B 刷新仍看得到**（云端是物理删除、不留痕迹，
> 而合并规则又要保留「本地独有」记录保护未上云的新数据）。
> 本期新增**删除日志（墓碑）集合**来显式传播删除。

---

## 0. 本期需上传 6 项

| # | 上传项 | 类型 | 是否必须 |
|---|---|---|---|
| 1 | `uniCloud-alipay/database/checkin_tombstones.schema.json` | DB Schema | ✅ 新集合 |
| 2 | `checkin_tombstones` 的 1 条索引 | 索引 | ✅ |
| 3 | `uniCloud-alipay/cloudfunctions/common/checkin-shared` | 公共模块 | ✅ **必须重传** |
| 4 | `uniCloud-alipay/cloudfunctions/diet` | 云函数 | ✅ |
| 5 | `uniCloud-alipay/cloudfunctions/workout` | 云函数 | ✅ |
| 6 | `uniCloud-alipay/cloudfunctions/study` | 云函数 | ✅ |

> ⚠️ **与 M2-B 不同：这次 `checkin-shared` 必须重传。**
> M2-B 时它「不需要重传」是因为那期没改它；本期给它新增了 `lib.js`
> 与 `recordTombstones` / `listTombstones` 两个导出。
> **不传的话三个云函数会报 `recordTombstones is not a function`。**
>
> ⛔ 仍然不要用「上传所有云函数、公共模块及 actions」——
> 它会连带重传 `uni-config-center`，导致 uni-id 配置丢失、登录全挂
> （M2-A 踩过，详见 `0.3.2-m2a-deploy-checklist.md` §7.1）。**逐个上传。**

### 上传顺序（有依赖关系）

**先 1 → 2 → 3，再 4 / 5 / 6。**

公共模块要在云函数之前：云函数运行时 `require('checkin-shared')`，
若先传云函数、后传公共模块，中间那段时间的删除调用会失败（标记会重试，不会丢数据，但会看到报错）。

## 2. 云端部署（HBuilderX，需手工操作）

### 2.1 上传 DB Schema ⬜

`uniCloud-alipay/database/checkin_tombstones.schema.json` → 右键 →「上传 DB Schema」

### 2.2 建 1 条索引 ⬜

控制台 →「云数据库」→ `checkin_tombstones` →「索引管理」→「新建索引」

| 索引名 | 字段与排序 | 唯一 |
|---|---|---|
| `idx_family_deleted` | `familyId` 升序, `deletedAt` 升序 | 否 |

> ⚠️ `familyId` 必须放第一位（所有查询都带它），顺序错了索引**静默失效且不报错**。
>
> ⚠️ 本集合**故意不加** `familyId + clientId` 唯一索引：
> 同一记录可能被删多次（删除 → 重新添加 → 再删除）。

### 2.3 上传公共模块 `checkin-shared` ⬜

`uniCloud-alipay/cloudfunctions/common/checkin-shared` → 右键 →「上传公共模块」

> **本期唯一改动公共模块的步骤，也是最容易被漏掉的一步。**
> 漏了的表现：`remove` 报 `recordTombstones is not a function`。

### 2.4 上传三个云函数 ⬜

`diet` / `workout` / `study` 各自右键 →「上传部署」

> 三个**都必须**重新上传：
> - `diet` / `workout`：`remove` 改为「删除 + 写墓碑」，并新增 `listTombstones`；
> - `study`：同上，且 `removePlan` 新增级联墓碑（删计划时为每个打卡补一条）。
>
> 只传其中一个的话，另外两个模块的删除仍然不会跨设备同步。

### 2.5 部署后自检 ⬜

浏览器 Console（H5 端，`uniCloud` 已挂在 window 上）：

```js
uniCloud.callFunction({ name: 'diet', data: { action: 'listTombstones', since: 0 } }).then(r => console.log(r.result))
uniCloud.callFunction({ name: 'workout', data: { action: 'listTombstones', since: 0 } }).then(r => console.log(r.result))
uniCloud.callFunction({ name: 'study', data: { action: 'listTombstones', since: 0 } }).then(r => console.log(r.result))
```

| 返回 | 含义 |
|---|---|
| `{code: 0, data: {items: []}}` | ✅ 全链路正常（还没删过东西，所以是空数组） |
| `{code: 0, data: {items: [{domain, clientId, date, deletedAt}]}}` | ✅ 正常，且已有墓碑 |
| `{code: 401, msg: '登录态无效或已过期'}` | 云函数 + 公共模块都正常，只是没登录态 |
| `{code: 400, msg: '未知操作: listTombstones'}` | ❌ 云函数是**旧版本**，重新上传 |
| 报 `recordTombstones is not a function` | ❌ **公共模块没传**（§2.3） |
| 报集合不存在 | ❌ schema 没传（§2.1） |
| `{code: 400, msg: '尚未加入家庭'}` | 鉴权通过，账号未加入家庭 |

## 4. 真机验收用例

两个微信号 A / B 在同一家庭下。每条都要 **B 重新进入页面**（触发拉取）。

### 4.1 基本删除同步（本次整改的目标）

| # | 操作 | 预期 | ✅ |
|---|---|---|---|
| 1 | A 删除一条饮食记录 | B 端该记录消失 | ⬜ |
| 2 | A 删除一条运动记录 | B 端该记录消失 | ⬜ |
| 3 | A 删除某天的学习打卡 | B 端该打卡消失 | ⬜ |
| 4 | A 删除一个**有历史打卡的学习计划** | B 端**计划与其全部打卡**一并消失（级联墓碑） | ⬜ |

### 4.2 不误删（比"能删掉"更重要）

| # | 操作 | 预期 | ✅ |
|---|---|---|---|
| 5 | B 端有**从未上云的本地老记录** | 仍在，不受任何删除影响 | ⬜ |
| 6 | B 离线新增一条（未上云），同时 A 删掉另一条 | B 自己的新增**仍在**，A 删的那条消失 | ⬜ |
| 7 | 同一条记录被反复拉取 | 不复活、不报错（幂等） | ⬜ |

### 4.3 冲突与边界

| # | 操作 | 预期 | ✅ |
|---|---|---|---|
| 8 | B 有一条**待同步编辑**的记录，A 把它删了 | B 端该记录消失，且待同步标记被清（不会反复重投） | ⬜ |
| 9 | A 删除后立刻在 B 端刷新两次 | 第二次无变化（游标生效，不重复处理） | ⬜ |
| 10 | 断网时 A 删除，恢复网络后 | 补传成功，B 端随后消失 | ⬜ |

---

## 5. ⚠️ 生效时点：历史删除不补

墓碑是**从本期部署完成之日起**才开始写的。

在此之前被删除的记录**没有墓碑**，它们在 B 端的残留**不会被追溯清理**。
若某台设备上还残留着「云端早已删除」的旧记录，**用户在本机手动删除一次即可**。

这是可接受的：那些记录本来就在用户自己的设备上、随时能删。

## 6. 故障排查

| 现象 | 排查 |
|---|---|
| `recordTombstones is not a function` | 公共模块 `checkin-shared` 没重传（§2.3） |
| `未知操作: listTombstones` | 对应云函数是旧版本，重新上传（§2.4） |
| 删除仍然不同步，但界面无报错 | 先看是否三个云函数都传了；再按 §2.5 自检，确认 `items` 里有墓碑 |
| 墓碑里有数据，但 B 端不删 | 检查前端是否重新构建发行了（§3） |
| 某条记录怎么都删不掉 | 可能是「存储键日期 ≠ 记录 date」的脏数据；已兼容（第 5 步修复），若仍出现请记录 id 排查 |
| 删除计划报「历史打卡较多，未清理完」 | 设计行为，**重试即可**；此时不会写墓碑，所以 B 端暂时不变（最终一致） |

## 7. 回滚

| 场景 | 处理 |
|---|---|
| 前端有问题 | 回退到上一个提交并重新构建；**云端数据不受影响** |
| 墓碑应用有误删 | 回退前端即可 —— 本地已删的记录会从云端重新拉回（云端若有），不会永久丢失 |
| 云函数有问题 | HBuilderX 重新上传上一版；墓碑集合留着无害 |
| 需要彻底回退 | 前端回退 + 三个云函数回退；`checkin_tombstones` 集合可保留（不再被写入） |

> 本期对 `diets` / `workouts` / `study_*` / `families` / `family_members` /
> `uni-id-users` 的**数据本身零改动**，只新增了一个集合。回滚不会损坏既有数据。
