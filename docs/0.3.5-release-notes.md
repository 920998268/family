**版本号：** v0.3.5
**发布日期：** 2026-09-14
**上一版本：** v0.3.4

## 版本概述

0.3.5 是**食谱 + 出行计划上云**版本（对应 `docs/0.3.5-m3-requirements-and-solution.md`，M3）。

**做了什么**：把「家庭每日食谱」与「家庭出行计划」两个模块从**纯本地存储**
接入云端（支付宝云），实现双端可见、离线可用、跨设备删除同步。

**为什么这两类**：M2 已把饮食 / 运动 / 学习三个打卡模块上云，
但「计划模块」（食谱、出行）仍只存在各自手机里 —— 而它们恰恰是**最需要两个人协作**的功能
（一个人买菜、另一个人掌勺；一个人定行程、另一个人收拾行李）。
本地存储下这些协作只能靠口头同步，是这个应用最明显的短板。

**本期与 M2 最本质的差别**：出行计划有一个**子实体**（行程明细），
而 M2 的两个模块都只有单层实体。这带来一个必须正面解决的问题 ——
**表单一次提交整份明细时，不能整包覆盖云端**，否则两个人同时编辑就会互相覆盖。
做法是把明细拆成独立集合 `travel_items`，逐条增 / 改 / 删（详见 §一.2）。

| 指标 | v0.3.4 | v0.3.5 |

> 与数据一行未动。回滚不会损坏既有数据。

## 一、新增能力

### 1. 两个新云函数 + 三个新集合

| 云函数 | 集合 | 说明 |
|---|---|---|
| `meal` | `meal_plans` | 食谱记录，**按日期**组织（同 `diets` 的形态） |
| `travel` | `travels` + `travel_items` | 出行计划（全量、不分日期）+ 行程明细（从属于计划） |

两个函数都沿用 M2 已成熟的形态：**记录级 CRUD + `familyId` 服务端推导 +
`clientId` 幂等键 + 删除写墓碑**。

> 计划与明细**合并在一个函数**里，是因为它们是主从关系：
> `addItem` 必须校验所属计划存在（否则会留下永久孤儿），
> `removePlan` 必须级联删除该计划的全部明细。

### 2. 行程明细拆成独立集合 —— 本期最有价值的一处改动

改造前，出行计划的编辑是**整包覆盖**：表单一次提交整份 `items` 数组，整包写回。
在本地存储上这不是问题（只有一台设备），但上云之后它意味着
**后写者覆盖前写者** —— 两个人同时给同一趟旅行安排行程，后保存的人会把对方的改动全部抹掉。
更隐蔽的是**删除**：整包覆盖下，「删掉一行」在云端是**不可见的事件**，
别的设备看到的只是「那一行还在旧数据里」。

改为明细独立集合后：

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 两人同时勾选**不同**明细 | 后写者覆盖前写者（丢一条勾选） | **两条都保留** |
| 两人同时勾选**同一条** | 取决于谁后到 | 服务端**串行翻转**，结果确定 |
| 删除一行明细 | 云端不可见，别的设备仍看得到 | 写 `travelItem` 墓碑，**逐条传播** |
| 一行内容改动 | 整份数组重写 | 只写那一条记录 |

配套的两个必要修复：明细 **id 必须稳定**（原实现每次编辑都会给全部明细重新生成 id，
云端按记录读写完全依赖它）、明细 **顺序必须显式存**（拆表后数组位置不再存在，
新增 `order` 字段）。

### 3. 跨设备删除同步扩展到新模块

0.3.4 建立的**墓碑（删除日志）**机制，本期把白名单由 4 个 domain 扩到 7 个：
新增 `mealPlan` / `travelPlan` / `travelItem`。

> ⚠️ 这里有一个**必须重传公共模块**的部署要点，见 §五.1 与部署清单 §2.3。
> 漏传的后果是「删除本地成功、别的设备永远看不到」且**全程零报错**。

### 4. 前端 store 接线

`meal` / `travel` 两个 store 接入云端，沿用已成熟的「本地优先」三件套：
先写本地让界面即时响应 → 登记待同步标记 → 后台尝试推送；
读取是「先渲染本地缓存（秒开）→ 云端拉取 → 合并回写」。

其中**勾选明细**走一条特殊路径：在线时直连服务端的**翻转**接口
（两端同时点同一条时结果确定），并用服务端返回的权威值校正本地；
离线 / 未登录时降级为排一条待同步标记兜底，保证离线勾选不会丢。

## 二、Bug 修复

本期在实现新功能的同时修掉了 4 个既有缺陷，其中 2 个是**上云之后才会暴露**的那一类。

### 1. ⚠️ 墓碑白名单漏项，导致「写」和「读」两条链路一起静默失效

`meal` / `travel` 两个云函数从写完那天起就在写 `mealPlan` / `travelPlan` / `travelItem`
三类墓碑，也在用 `listTombstones({ domains: ['mealPlan'] })` 读 ——
但墓碑白名单 `TOMBSTONE_DOMAINS` 一直只有 4 个（M2 时代的 `diet` / `workout` /
`studyPlan` / `studyCheckin`）。

这个白名单是**双刃**的：

| 链路 | 用它的地方 | 漏改的后果 |
|---|---|---|
| **写** | `buildTombstoneDocs` 对未知 domain 直接 `return []` | 墓碑**一条都不写** |
| **读** | `listTombstones` 用 `isTombstoneDomain` 过滤 `domains` | 过滤成空 → 返回 `{ items: [] }` |

于是「删除本地成功、墓碑不存在、别的设备永不同步」，**没有任何报错**。
已在本期扩到 7 个，并加了「两端白名单**逐值**相等」的守卫
（只数个数在「只加了一部分」时会假通过）。

### 2. ⚠️ 出行明细 id 在每次编辑后全部失效

`TravelService.normalizeItems()` 在每次 `update` 时给**全部明细重新生成 id**。
纯本地场景看不出来（store 会重新加载），但云端「按明细记录读写」完全依赖稳定 id ——
任何一次计划编辑之后，`toggleItem` / `updateItem` 拿到的 id 立即失效。

已改为**保留已有 id、只为新行生成**。

### 3. 出行表单回填明细时丢掉 id

承上一个问题：编辑页把计划明细回填到表单时没有带上 `id`。
后果是「打开编辑 → 保存」会被判定为**旧行全删 + 新行全增** ——
云端删一轮又建一轮，明细 id 全变、`travelItem` 墓碑乱飞。
已在回填时保留 `id`。

### 4. `removePlan` 违反「墓碑无条件写」

`study` / `travel` 的 `removePlan` 原先写成「计划记录不存在就早返回」，
跳过了墓碑写入 —— 而 0.3.4 确立的规则是**无论记录是否存在都要写墓碑**。

这是「计划已删、写墓碑失败 → 客户端重试」时**唯一能补写墓碑的机会**，
早返回就等于永久丢墓碑。已统一为：父墓碑无条件写，级联只在父记录存在时做。

## 三、优化改进

1. **长度上限的「三角闭合」守卫**：前端 `limits.ts` ↔ 云侧 `lib.js` ↔ DB Schema 的
   `maxLength` 三处必须一致。只写「A === B」的断言在两者**一起改错**时形同虚设，
   所以额外留了一处**绝对值基准** + 方向性断言「schema 不得比 lib 更严」；
2. **全 domain 接通守卫**：给 7 个 domain 各放一条本地记录 + 各排一条待同步标记，
   `flush()` 后要求全部成功、零丢弃 —— 专抓「漏接一条推送分支」这类静默失败
   （同步层的 `default` 分支会把未知 domain 当成「本地无内容可推」直接放弃）；
3. **云调用接线守卫**：断言每个远端仓储方法打出的云函数名与 `action` 名 ——
   action 写错在运行时是**静默 400**，这是唯一的把关点；
4. **两层串联契约守卫**：把前端上行产物直接喂给云函数入参校验器
   （`validateMealPayload(toCloudMeal(x)).ok`），映射层与云端契约漂移时立刻失败；
5. **每一处新守卫都做了变异验证**：故意改坏实现，确认对应用例会红。
   本期累计验证 29 组变异（第 3 步 9 组 / 第 5 步 6 组 / 第 6 步 8 组 / 第 7 步 12 组，
   含跨步复核），全部被捕获。

## 四、已知限制

1. ✅ **云端部署（9 项）与 38 条真机用例已于 2026-09-14 全部通过**。
   步骤与结果见 `docs/0.3.5-m3-deploy-checklist.md` §7。
   其中「墓碑通路专项验证」也已通过 —— 注意单看 `listTombstones` 返回空数组
   无法区分「没有墓碑」和「白名单没生效」，必须走一次「新建 → 删除 → 查集合」。
2. **老数据不主动上云**：M3 之前存在本机的食谱 / 出行记录仍只在本机可见，
   批量导入与 M4 的账本一起做（M2 时就明确留到 M4）。
3. **无实时推送**：他人改动需要重新进入页面才能看到（仍为「进入页面拉取」）。
4. **进出详情的明细拉取是 N+1**：进入出行页会「拉全部计划 + 逐个计划拉明细」，
   `listPlans` 的聚合明细**故意不被信任**（它有 500 条上限、会被截断）。
   家庭场景下计划数量有限，可接受；计划数增长后可改为按需拉取。
5. **墓碑不自动清理**：超过 180 天的墓碑不再返回但也不会被删除（同 0.3.4）。
6. **重试超限仍会丢弃标记**：标记连续失败 5 次后放弃，该记录停留在本地。
   这是 0.3.4 就遗留的独立课题。
7. **账本仍为 localStorage 实现**（M4）。
8. 支付宝云免费版 **2026-10-04 到期**，需关注续期。

## 五、升级与发布说明

### 1. 云侧部署（**必须在 HBuilderX 手工完成**，共 9 项）

支付宝云不支持 CLI 发行，以下操作无法通过命令行完成。
**逐项清单见 `docs/0.3.5-m3-deploy-checklist.md`**，摘要：

| # | 上传项 | 说明 |
|---|---|---|
| 1-3 | DB Schema `meal_plans` / `travels` / `travel_items` | 三个新集合 |
| 4 | 云函数 `meal` | 食谱 |
| 5 | 云函数 `travel` | 出行计划 + 行程明细 |
| 6 | 公共模块 `common/checkin-shared` | ⚠️ **本期必须重传**（`TOMBSTONE_DOMAINS` 4 → 7） |
| 7 | 云函数 `study` | ⚠️ **本期必须重传**（`removePlan` 墓碑口径统一） |
| 8 | DB Schema `checkin_tombstones` | 仅字段说明文字更新（文档性，可选） |
| 9 | 6 条索引 | 见部署清单 §2.6 |

**先 1 → 2 → 3 → 6（公共模块），再 4 / 5 / 7（云函数）。**
公共模块必须在云函数之前 —— 云函数运行时会 `require` 它。

> ⛔ **不要用「上传所有云函数、公共模块及 actions」**：
> 该操作会连带重传 `uni-config-center`，而 HBuilderX 的公共模块来源目录里
> 并没有 `uni-id/config.json`，重传会导致**所有登录/注册接口报
> `Invalid uni-id config file`**（M2-A 时实际踩过）。

> 微信公众平台合法域名本期**无需改动**，具体值见 `docs/0.3.2-m2a-deploy-checklist.md`。

### 3. 部署后自检（不用真机，1 分钟）

H5 页面 Console 中执行（**三条都要看**）：

```js
uniCloud.callFunction({ name: 'meal',   data: { action: 'list', date: '2026-09-12' } }).then(r => console.log(r.result))
uniCloud.callFunction({ name: 'travel', data: { action: 'listPlans' } }).then(r => console.log(r.result))
uniCloud.callFunction({ name: 'meal',   data: { action: 'listTombstones', since: 0 } }).then(r => console.log(r.result))
```

| 返回 | 含义 |
|---|---|
| `{code: 0, data: [...]}` | ✅ 全链路正常 |
| `未知操作: xxx` | ❌ 云函数还是旧版本，重新上传 |
| `Cannot find module 'checkin-shared'` | ❌ 公共模块没传成功 |
| 报集合不存在 | ❌ schema 没传 |

> ⚠️ **`listTombstones` 返回空数组不能说明问题** —— 「没有墓碑」和
> 「白名单没生效」长得一模一样。必须按部署清单 §2.7 的「墓碑通路专项验证」
> 走一遍：**新建一条食谱 → 删除 → 到控制台看 `checkin_tombstones` 里有没有记录**。
