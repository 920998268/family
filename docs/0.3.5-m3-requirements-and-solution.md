## 1. 背景与范围

### 1.1 为什么是这两类

M3 的范围在 2026-09-12 的「M2 范围歧义」决策中已缩减：**学习打卡并入 M2-B 完成**，
M3 只剩 **食谱** 与 **出行计划** 两类（`backend-uniCloud-implementation.md` §4）。

### 1.2 现状盘点

两个模块的**本地实现早已完成**，本期的实质是「把已有模块搬上云」，不是从零开发：

| 模块 | 本地实现 | 存储形态 | 服务接口 |
|---|---|---|---|
| 食谱 | `src/pages/plan/meal.vue`<br>`src/services/MealService.ts`<br>`src/repositories/MealPlanRepository.ts` | `family.meal.v1.<date>`<br>**按日期分区**（同 M2-A 的 diet） | `listByDate` / `getAll` / `add(date, draft)` / `update(date, id, patch)` / `remove(date, id)` |
| 出行 | `src/pages/plan/{travel,travel-form}.vue`<br>`src/services/TravelService.ts`<br>`src/repositories/TravelRepository.ts` | `family.travel.plans.v1`<br>**全量列表**，计划内**内嵌 `items` 数组** | `list` / `add` / `update(id, patch)` / `setStatus` / `toggleItem` / `remove` |

数据模型（`src/types/models.ts`）：

```
MealPlan   { id, date, slot: breakfast|lunch|dinner|snack,
             dishName, ingredients, cook, done: boolean, note }
TravelPlan { id, title, startDate, endDate, destination, members: string[],
             budget: number, status: planned|ongoing|done|cancelled, note,
             items: TravelItem[] }          ← 内嵌
TravelItem { id, time, activity, note, done: boolean }
```

> Store / Service / 页面结构完整，**UI 基本不需要改造** —— 这是 M2 建好的
> 鉴权 / 同步服务 / 离线标记 / 映射层基建第二次发挥价值。

### 1.3 出口验收标准

1. A 新增 / 编辑 / 删除一条食谱记录 → B 重新进入页面后可见、可消失（删除靠墓碑传播）；
2. A 新增 / 编辑 / 删除一个出行计划 → B 同步；**删除计划时其行程明细一并消失**；
3. A 勾选 / 取消勾选某条行程明细 → B 同步，且**逐项生效、不整包覆盖**；
4. B 离线期间勾选两条明细并改了计划标题 → 联网后全部上云，**不丢任何一项**；
5. **两人几乎同时勾选同一出行计划的不同明细 → 两条都保留**（这是拆明细集合的直接收益）；
6. 设备上「从未上云的历史本地食谱 / 出行数据」在本机可见，**不被云端合并误删**；
7. 历史本地数据在本机可正常编辑，改动同样能上云。

## 3. 设计

### 3.1 云侧集合与字段

字段名**与前端模型保持一致**（映射层只做 `null` ↔ `undefined` 换算，不做重命名），
统一附 `familyId` / `clientId` / `createdByUid` / `createdAt` / `updatedAt`。

**`meal_plans`（食谱记录）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `familyId` | string | 家庭归属（服务端推导） |
| `clientId` | string | 幂等键 = 前端 `MealPlan.id` |
| `date` | string | `YYYY-MM-DD` |
| `slot` | string | `breakfast` / `lunch` / `dinner` / `snack` |
| `dishName` | string | 菜名，必填，≤ 40 |
| `ingredients` | string | 食材，可空串，≤ 200 |
| `cook` | string | 掌勺人，可空串，≤ 20 |
| `done` | boolean | 是否已执行 |
| `note` | string | 备注，可空串，≤ 100 |

> ⚠️ `meal_plans` 的字段名 **不是** 路线图 §7.1 早期设计稿里的 `mealType` / `dishes`。
> 以本表为准（与前端 `MealPlan` 对齐），§7.1 一并校正。

**`travels`（出行计划）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `familyId` / `clientId` | string | 同上 |
| `title` | string | 标题，必填，≤ 40 |
| `startDate` / `endDate` | string | `YYYY-MM-DD`，`endDate ≥ startDate` |
| `destination` | string | 目的地，可空串，≤ 40 |
| `members` | array\<string\> | 参与成员 id 列表（**去重、剔除空值**） |
| `budget` | number | 预算，≥ 0，缺省 0 |
| `status` | string | `planned` / `ongoing` / `done` / `cancelled` |
| `note` | string | 备注，可空串，≤ 200 |

**`travel_items`（行程明细）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `familyId` / `clientId` | string | 同上；`clientId` = 前端 `TravelItem.id` |
| `travelId` | string | 所属出行计划的 `clientId`（主从约束） |
| `order` | number | 展示顺序（表单行序，0 起） |
| `time` | string | 时间描述，可空串，≤ 20（如「上午 9:00」） |
| `activity` | string | 活动，必填，≤ 40 |
| `note` | string | 备注，可空串，≤ 100 |
| `done` | boolean | 是否已完成 |

> `order` 是本期新增字段：拆表后「表单里的行序」不再由数组位置隐式表达，
> 必须显式存下来，否则两边看到的明细顺序可能不一致。

**索引（6 条，全部为复合索引，`familyId` 必须放第一位）**

| 集合 | 索引名 | 字段与排序 | 唯一 | 用途 |
|---|---|---|---|---|
| `meal_plans` | `idx_family_client` | `familyId`↑, `clientId`↑ | ✅ | 幂等键 |
| `meal_plans` | `idx_family_date` | `familyId`↑, `date`↑ | 否 | 按日期拉取 |
| `travels` | `idx_family_client` | `familyId`↑, `clientId`↑ | ✅ | 幂等键 |
| `travels` | `idx_family_start` | `familyId`↑, `startDate`↓ | 否 | 列表排序（与本地 `list()` 的降序一致） |
| `travel_items` | `idx_family_client` | `familyId`↑, `clientId`↑ | ✅ | 幂等键 |
| `travel_items` | `idx_family_travel` | `familyId`↑, `travelId`↑, `order`↑ | 否 | 取某计划的明细 + 级联删除定位 |

> `travel_items` **不加** `familyId + travelId + order` 唯一索引：
> 用户完全可能把两行都留空/写同样的时间，顺序冲突用排序稳定化处理即可，
> 加唯一索引只会让正常编辑报错。

### 3.2 云函数与路由

**`meal`**（对应集合 `meal_plans`）

| action | 说明 |
|---|---|
| `list` | 入参 `{ date }`，返回该日期的食谱记录 |
| `add` / `update` / `remove` | 记录级 CRUD；`remove` 先删记录、后写墓碑 |
| `listTombstones` | 墓碑增量拉取（`domain: 'mealPlan'`） |

**`travel`**（对应集合 `travels` + `travel_items`）

| action | 说明 |
|---|---|
| `listPlans` | 全量返回本家庭出行计划（含 `items` 聚合结果，供首屏直接渲染） |
| `addPlan` / `updatePlan` / `removePlan` | 计划级 CRUD；`removePlan` **级联删明细 + 逐条写墓碑**（先删明细、再删计划） |
| `addItem` / `updateItem` / `toggleItem` / `removeItem` | **明细级 CRUD**（本期新增的能力，是「不整包覆盖」的关键） |
| `listTombstones` | 返回 `travelPlan` + `travelItem` 两类墓碑 |

级联删除沿用 `study` 已验证的做法：`collectItemRefs` → 分批删 → **未删完（truncated）时不删计划、不写墓碑**，返回可重试错误。

**拉取通路的口径（三条，注意与打卡不同）**：

|---|---|---|

> 漏任何一处，新模块的删除就**静默不传播** —— 不报错、界面正常、就是删不掉。
> 实施时必须一次性改全，并用测试守住。

### 3.5 本期最大的改动：明细的记录级化

这是 M3 与 M2 最本质的差异，也是最容易做错的地方。

**现状问题**：`TravelService` 的写入是**整包覆盖** ——

- `update()` 里 `this.repository.saveAll(plans)` 重写整个出行列表；
- `toggleItem()` 也是走 `update()` 把**整个 `items` 数组**写回去；
- 且 `normalizeItems()` 在**每次 update 时给全部明细重新生成 id**。

后者还有一个连带后果：**任何一次计划编辑之后，所有明细 id 都会变** ——
`toggleItem` 拿到的 id 在改过表单之后就失效了。这在纯本地场景下不易察觉
（store 会重新加载），但**云侧记录级 CRUD 必须依赖稳定的明细 id**。

**改造方案**：

1. `TravelItemDraft` 增加可选 `id`；`normalizeItems` **保留已有 id**，只为新行生成；
2. 新增纯函数 `computeItemDiff(original, submitted)` → `{ added, updated, removed }`
   （纯函数、可单测，符合本项目把控制流抽出单测的一贯做法）；
3. 表单提交时：**计划本体走 `updatePlan`，明细走 diff 后的逐条 `addItem` / `updateItem` / `removeItem`**；
4. 详情页勾选走 `toggleItem`（记录级，只写 `done`），**不再写整个数组**；
5. `TravelService` 的本地写入同样改为记录级，使本地与云端语义一致
   （否则「本地整包 / 云端记录级」两套语义会在离线补传时打架）。

> 收益不只是并发安全：明细的删除因此可以**逐项传播**到其他设备
> （`travelItem` 墓碑），而整包覆盖下「删掉一行」在云端是不可见的事件。

## 4. 与 M2 的差异点（实施时最容易照抄出错的地方）

| # | 差异 | 说明 |
|---|---|---|
| 1 | **明细拆表** | M2 的「主从」只有一层（计划 → 打卡）；本期是 计划 → 明细，且明细**逐项编辑**（M2 的打卡是整条增删） |
| 2 | **明细顺序显式化** | 拆表后数组位置丢失，新增 `order` 字段 |
| 3 | **明细 id 必须稳定** | 见 §3.5，`normalizeItems` 重新生成 id 的旧行为必须先修掉 |
| 4 | **`members` 是数组字段** | M2 所有集合都是标量字段；数组要做去重、剔除空值、长度上限，映射层与 schema 都要处理 |
| 5 | **墓碑 domain 一次加 3 个** | M2-A/M2-B 时墓碑还不存在（0.3.4 才落地）；本期是**第一次**在墓碑存在的前提下新增模块 |
| 6 | **两个模块通路口径不同** | 食谱按日期（同 diet），出行计划全量 + 明细按计划（同 study 的变体） |

## 5. 风险与坑

1. **墓碑 domain 六处硬编码**（见 §3.4）：最典型的「静默失败」风险；
2. **`normalizeItems` 的 id 再生**（见 §3.5）：不修则记录级 CRUD 无法成立；
3. **`members` 数组的脏数据**：`MemberMultiSelect` 可能给出重复或已删除成员 id，
   校验层要**去重 + 剔除空值**，但不因成员不存在而丢弃整条记录
   （成员被移除不该让出行计划消失）；
4. **UI `maxlength` 必须补**：云端 lib 有长度上限而表单没有 —— 这个坑在 M2-A/M2-B
   都出现过（超长输入本地写入成功、推云端 400、重试 5 次后**丢弃标记** = 静默丢数据）。
   本期在表单上加 `:maxlength`，并加「UI 上限 == lib 上限」的一致性守卫；
5. **路线图 §7.1 的文档缺陷**：`meal_plans` / `travels` / `travel_items` /
   `transactions` / `sync_meta` 五行**少了「状态」列**（说明文字掉进了状态列），
   且 `meal_plans` / `travel_items` 的字段是早期设计稿。本方案第 1 步一并校正。

## 6. 明确不做

1. 不改 M2 已有的合并语义与墓碑语义（只做 domain 扩展与新通路）；
2. 不做明细的实时推送 —— 仍是「进入页面拉取」；
3. 不做食谱的模板 / 常用菜复用（`product-design.md` 第 110 行提到的后续增强）；
4. 不做「预算 ↔ 账本联动」（账本属 M4）；
5. 不做历史本地数据的批量导入（M4 的老数据迁移入口）；
6. 不为 `travel_items` 加 `familyId + travelId + order` 唯一索引（见 §3.1）。

### 第 2 步的实现要点（供第 5~7 步接线时对照）

| 原语 | 契约 |
|---|---|
| `normalizeTravelMembers(value)` | 去重 + 剔除空值/非字符串，**保持原顺序**；非数组 → `[]` |
| `normalizeTravelItems(drafts, generateId?)` | 补 id（**保留草稿已有的**）、按下标写 `order`、文本字段收敛成字符串、`done` 非 `true` 即 `false` |
| `computeItemDiff(original, submitted, generateId?)` | → `{ added, updated, removed, unchanged }`；带未知 id 视为新增且**沿用该 id**；同一 id 重复出现时第二条起分配新 id |
| `sortTravelItems(items)` | 按 `order` 稳定排序；**缺失 `order` 的老数据按下标参与排序** |
| `TravelItemDraft` | `Omit<TravelItem, 'id' \| 'order'> & { id?: string }` —— 草稿不带 `order`，顺序由下标决定 |

两条刻意的行为（已用测试固化，接线时别当成 bug）：

1. **中间插入一行会让其后所有明细被判为 `updated`** —— 云端确实需要把新顺序写下去，
   不能靠数组位置隐式表达；
2. **`order` 在校验里必须是「可选」** —— `TravelRepository` 是「校验不通过即丢弃」，
   改成必填会让全部历史出行计划在读取时**静默消失**。

> 部署与验收见 `0.3.5-m3-deploy-checklist.md`（第 8 步产出）。

### 第 3 步的实现要点（第 4 步写 `index.js` 时直接照此接线）

两个 lib 合计导出 42 个符号；第 4 步的路由与 schema 只需消费下表这些。

**`meal/lib.js`**

| 导出 | 契约 |
|---|---|
| `MEAL_SLOTS` | `['breakfast','lunch','dinner','snack']`，与前端 `MEAL_TYPES` 逐项一致（测试锁住） |
| `validateMealPayload(payload)` | → `{ clientId, date, slot, dishName, ingredients, cook, done, note }`；`date` 必须 `YYYY-MM-DD` |
| `mergeMealPatch(existing, patch)` | **`clientId` 与 `date` 不可由 patch 修改**（见下） |
| `validateMealQuery(payload)` | → `{ date }`；只支持按日期查（不做 diet 的区间查询 —— 没有调用方） |
| `toClientMeal(row)` | 输出必须被前端 `validateMealPlan` 接受 |
| `DISH_NAME_MAX` / `INGREDIENTS_MAX` / `COOK_MAX` / `NOTE_MAX` | 40 / 200 / 20 / 100，与 `MEAL_LIMITS` 逐项一致 |

**`travel/lib.js`**

| 导出 | 契约 |
|---|---|
| `TRAVEL_STATUSES` | 与前端 `TRAVEL_STATUSES` 逐项一致（测试锁住） |
| `validatePlanPayload(payload)` | → `{ clientId, title, startDate, endDate, destination, members, budget, status, note }` |
| `mergePlanPatch(existing, patch)` | `clientId` 不可改 |
| `normalizeMembers(value)` | 去重 + 剔除空值/非字符串、保序；**与前端 `normalizeTravelMembers` 在穷举输入上逐一致** |
| `validateItemPayload(payload)` | → `{ clientId, travelId, order, time, activity, note, done }`；`order` 缺省为 0 |
| `mergeItemPatch(existing, patch)` | **`clientId` 与 `travelId` 都不可改** |
| `validateItemQuery(payload)` | → `{ travelId }` |
| `deleteInBatches(deleteBatch, options)` | → `{ deleted, rounds, truncated }`；**与 `study` 的同名函数行为等价**（测试在穷举序列上比对） |
| `toClientPlan(row, items)` | 第二参数是聚合好的明细；缺省给 `[]`（前端要求 `Array.isArray`） |
| `toClientItem(row)` | `order` 恒为有限数（缺省 0）—— 云端返回顺序不保证稳定 |
| `TITLE_MAX` / `DESTINATION_MAX` / `NOTE_MAX` / `ITEM_TIME_MAX` / `ITEM_ACTIVITY_MAX` / `ITEM_NOTE_MAX` | 40 / 40 / 200 / 20 / 40 / 100，与 `TRAVEL_LIMITS` 逐项一致 |
| `BUDGET_MIN` / `BUDGET_MAX` / `MEMBERS_MAX` | 0 / 100000000（= 前端 `numberError` 边界）/ 50（防御性） |

四个刻意的行为（已用测试固化，第 4~7 步接线时别当成 bug）：

1. **可空文本一律落 `''` 而绝不落 `null`**（`ingredients` / `cook` / `note` / `destination` /
   明细 `time` / 明细 `note`）。前端 `validateMealPlan` / `validateTravelPlan` 要求这些字段是
   **字符串**，落 `null` 会让整条记录被判非法、被仓储层**静默丢弃** ——
   而本地写入是成功的，界面一切正常，属于最难对照发现的一类丢数据。
2. **`done` 只认严格布尔 `true`**，`'true'` / `1` / 缺省一律归 `false`（不做真值猜测）。
3. **`meal` 的 `date`、`travel_items` 的 `travelId` 都不允许通过 patch 修改**：
   两者都是「按什么维度拉取」的定位键（日期 / 所属计划），改了会让记录在原有拉取通路上
   凭空消失 —— 旧位置以为被删、新位置从未拉过。前端也从不做这两种改动。
4. **`members` 里的超长 id 是云端独有的防御**（前端 `normalizeTravelMembers` 只 `trim` 不判长）。
   这是唯一一处刻意的两端行为差异，已在测试里显式标注，且正常不可能触发
   （`createId()` 产出约 41 字符，上限 64）。

>
> - `travel/lib.js` 与 `study/lib.js` 的 `deleteInBatches` 是**逐字一致的两份拷贝**

>   枚举 7 个云函数的 lib 并断言源码里**不含 `require(`**。
