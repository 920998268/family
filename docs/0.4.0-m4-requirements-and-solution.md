## 1. 背景与范围

### 1.1 为什么是这两件事

M4 是 M2（打卡上云）与 M3（计划上云）之后的最后一个业务里程碑。路线图把它定义为两件事：

1. **收支账本远程化** —— 六个业务模块里最后一个仍只存在于本机的模块；
2. **「本地数据导入云端」入口** —— 从 M2-A 起就明确「老数据不主动上云，批量导入留到 M4」，
   这句话在四处文档里都写着（`0.3.2-m2a-requirements-and-solution.md` §1.3 与 §9、
   `0.3.3-m2b-requirements-and-solution.md` §2 表第 4 行、`0.3.4-cross-device-delete-sync.md` §2 第 3 行、
   `0.3.5-m3-requirements-and-solution.md` §6 第 5 条）。

**为什么两件事必须同一版交付**：账本一旦上云，「老数据上不去云」的影响面就从
「某一类模块」扩到「所有模块」—— 用户会把「我的历史记录怎么只有这台手机有」
归因于整个上云能力。所以本期的验收口径是**导入入口与账本上云同时可用**，不拆版发布。

### 1.3 出口验收标准

1. A 新增 / 编辑 / 删除一笔收支 → B 重新进入账本页后可见 / 变更 / 消失（删除靠墓碑传播）；
2. A 切换到上个月 → 该月数据完整、**汇总数字正确**（不是只拉当天，见 §3.4）；
3. 点「导入云端」后，本机全部老数据（饮食 / 运动 / 学习计划 / 学习打卡 / 食谱 /
   出行计划 / 出行明细 / 收支）在 B 设备上可见；
4. **导入可重复执行且不产生重复记录**；中途失败后重跑能接着完成；
5. 导入结束时**报数**：成功 / 已在云端（幂等跳过）/ 失败三类条数，以及被归一的字段明细 ——
   **不允许出现「导入成功、但少了一部分」**；
6. 设备上「从未上云的历史记录」在本机可见、可编辑，**不被云端合并误删**；
7. 离线记一笔账 → 联网后自动上云，不丢；
8. 两台设备同时各记一笔 → 两条都在（记录级，无整包覆盖）；
9. 编辑态下日期选择器**不可改**（§3.6 第 1 条）。

## 2. 关键决策

### 2.1 本轮已确认（2026-09-14）

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| 1 | 云函数划分 | **新增独立云函数 `ledger`**（单表 `transactions`） | 沿用 M2 确立的判据「**存在主从关系才合并**」：账本没有子实体、不涉及级联删除，与 `meal` 同构，没有并入其它函数或拆成多个的理由 |
| 2 | 版本号 | **0.4.0** | 跨里程碑边界，0.3.x 到此告一段落 |
| 3 | 老数据的传输方式 | **新增批量 action `importAll`**，客户端**分批 50 条**下发 | 逐条调 `add` 在千条量级要上千次往返（数分钟、不可中断重来）；批量把一次导入压到几十次调用。云端仍**逐条严格校验**，一条不合法不影响整批 |
| 4 | 导入范围 | 8 个 domain 的业务数据 | **不含**个人档案与家庭成员（M1 已上云）；**不含**常用食物（`favorite_foods` 只在云端沉淀，本机没有副本） |
| 5 | 编辑态改日期 | **编辑态禁用日期选择器**（新增态可改） | `date` 既是本机分区键、又是云端拉取维度；允许改就要引入「跨分区移动」语义（删旧 + 建新 + 墓碑），复杂度不成比例。见 §3.6 |
| 6 | 服务空间到期 | **不列为本期风险**（用户已确认：到期后自行切换其他模式） | 但由此推出一条设计约束：**不使用支付宝云特有的 API / 方言 / 专用扩展**，云函数与 schema 保持可迁移（见 §5 末） |

### 2.2 实施默认项（沿用既有约定，不再单独决策）

| # | 项 | 约定 |
|---|---|---|
| 7 | 离线与删除同步 | **直接复用** `pendingSync` + `checkin_tombstones`，不新增机制；`domain` 由 7 个扩到 8 个（见 §3.4） |
| 8 | 记录标识 | 沿用「客户端生成的 `id` 作为幂等键」，映射层改名为 `clientId`；**前端模型不需要为此新增字段**（见 §3.6 第 3 条） |
| 9 | 数据归属 | 每条记录带 `familyId`，服务端从登录态推导，**不接受客户端传入** |
| 10 | 成员归属 | `memberId` 可选；传入但**不属于本家庭时剔除该字段**，不因此拒绝整条记录（同 M3 对 `members` 的处理：成员被移出不该让账目消失） |

## 3. 设计

### 3.1 云侧集合与字段

**`transactions`（收支记录）** —— 字段名与前端模型一致（映射层只做 `null` ↔ `undefined` 换算，不做重命名），
统一附 `familyId` / `clientId` / `createdByUid` / `createdAt` / `updatedAt`。

| 字段 | 类型 | 说明 |
|---|---|---|
| `familyId` | string | 家庭归属（服务端推导） |
| `clientId` | string | 幂等键 = 前端 `Transaction.id`，≤ 64 |
| `type` | string | `income` / `expense` |
| `amount` | number | 金额，0.01 ~ 1e8（与前端 `numberError` 的边界逐项一致） |
| `category` | string | 分类，必填，≤ 20 |
| `date` | string | `YYYY-MM-DD`（**分区键，不可改**） |
| `memberId` | string \| null | 记账成员，可选。**id 型可选字段，不适用「可空文本落 `''`」规则**（见 §3.3） |
| `note` | string | 备注，可空串，≤ 100 |
| `createdByUid` | string | 创建者 uid（审计用） |
| `createdAt` / `updatedAt` | timestamp ×2 | **毫秒时间戳**，服务端生成 |

> ⚠️ 路线图 §7.1 早期设计稿写的是
> `familyId, type(income/expense), category, amount, date, note, memberId, createdAt` ——
> 缺 `clientId`（幂等键）、缺 `updatedAt`。**以本表为准**，§7.1 一并校正。
>
> ⚠️ `category` **刻意不做白名单枚举校验**。前端分类是常量表
> （`EXPENSE_CATEGORIES` 8 项 / `INCOME_CATEGORIES` 6 项），而历史数据里的分类
> 可能不在当前表内（用户改过分类常量就会发生）。加了白名单，这些历史记录会**导入失败**。
> 只校验「非空字符串 + 长度上限」。

**索引（2 条，全部为复合索引，`familyId` 必须放第一位）**

| 索引名 | 字段与排序 | 唯一 | 用途 |
|---|---|---|---|
| `idx_family_client` | `familyId`↑, `clientId`↑ | ✅ | 幂等键 |
| `idx_family_date` | `familyId`↑, `date`↑ | 否 | 按月份区间拉取（§3.4） |

### 3.2 云函数 `ledger` 与路由

| action | 说明 |
|---|---|
| `list` | 入参 `{ from, to }`（闭区间，`YYYY-MM-DD`），返回该区间内本家庭的收支记录 |
| `add` / `update` / `remove` | 记录级 CRUD；`remove` **先删记录、后写墓碑**（墓碑**无条件写**） |
| `importAll` | 批量导入：入参 `{ records: [...] }`（单批上限 50），**逐条**校验 + 幂等写入，返回 `{ created, duplicated, invalid: [{ clientId, msg }] }` |
| `listTombstones` | 墓碑增量拉取（`domain: 'transaction'`） |

**与既有云函数的关系**

- `remove` 与 `meal/index.js` 的 `removeMeal` **同构**：先删记录、后写墓碑；
  记录不存在也要写；墓碑里的 `date` 必须尽量带上（账本本地同样按日期分区，
  带上日期别的设备就能直接定位分区，落空串只能全量扫描兜底）；
- `update` 的 `date` **不可改**：`mergeTransactionPatch` 写死取既有记录的 `date`
  —— 改日期会让记录在「按区间拉取」时凭空消失（旧区间拉不到、新区间从没推过）。
  前端 `TransactionPatch` 本来就不含 `date`，与 `meal` 完全一致；
- `importAll` 是本项目**第一个批量写接口**。它**不引入任何新的写入规则**：
  复用与 `add` 相同的校验器与幂等查找，只是把「一次一条」变成「一次一批、逐条独立成败」。
  某条不合法 → 记进 `invalid` 并继续，**绝不因一条脏数据让整批失败**；
- `memberId` 用 `checkin-shared` 的 `resolveMemberId` 解析，取不到本家庭的成员就
  **剔除该字段**（不是拒绝记录）。

### 3.3 前端映射层与调用封装

- `src/utils/cloudMap.ts` 增加一组双向映射 `toCloudTransaction` / `fromCloudTransaction` /
  `mapCloudTransactions`，沿用既有约定：
  - `clientId: entry.id`；
  - **`memberId` 走 `upId` / `asString(...) || undefined`**（与 diet 完全同口径）——
    **不适用**「可空文本落 `''`」那条规则：`optionalIdError` 把空串判为**非法**，
    落空串会让整条记录被仓储层**静默丢弃**。这是本项目最隐蔽的一类丢数据（见 §5 第 4 条）；
  - `note` / `category` 是文本字段，落 `''` 而不是 `null`；
  - `amount` 上传前收敛成有限数（`Number.isFinite` 不成立时按 0 处理，让云端校验器
    **报错**，而不是静默塞一个值）；
- `src/unicloud/index.ts` 增加 `callLedger` 与 5 个业务方法
  （`listCloudTransactions` / `addCloudTransaction` / `updateCloudTransaction` /
  `removeCloudTransaction` / `importCloudTransactions`）；
- `src/repositories/remote/LedgerRemoteRepo.ts`：与既有远端仓储同风格 ——
  只把云函数名与映射挡在仓储层，不含业务逻辑。

### 3.4 同步与离线

沿用 M2 / M3 的三件套，**不新增机制**，只做扩展：

| 位置 | 改动 |
|---|---|
| `checkin_tombstones.schema.json` | `domain` 说明与枚举 → 8 个值 |
| `checkin-shared/lib.js` | `TOMBSTONE_DOMAINS` 7 → 8 |
| `src/utils/pendingSync.ts` | `SyncDomain` 类型与 `SYNC_DOMAINS` 7 → 8 |
| `CheckinSyncService` | 新增依赖（`ledgerRepository` / `ledgerRemote`）+ `pullTransactions(from, to)` + `pushTransaction` 分支 + 墓碑 `transaction` 删除分支 |
| `src/services/index.ts` | 工厂接线 |

**拉取通路的口径（一条，但与 M2 / M3 都不同）**

| 通路 | 入参 | 参照与差别 |
|---|---|---|
| `pullTransactions(from, to)` | **日期区间** | M2 是「按单日」（diet / meal / studyCheckin），M3 是「全量 + 按所属计划」（travel）；账本**必须按区间** |

> ⚠️ **为什么不能只按单日拉**：`ledger.vue` 的汇总卡（收入 / 支出 / 结余）是对
> **当前选中月份**的全部记录求和（`summarize(filteredEntries)`）。只拉当天的话，
> 月汇总会基于残缺数据算出**明显偏小的数字** —— 用户立刻会察觉「我的账是不是记错了」。
> 按月拉区间，一次请求正好覆盖页面真实需要的数据。
>
> **为什么不做「全量拉」**：账本没有「所有月份一屏看」的页面，全量拉只会把
> 无界的数据量搬到每次进页面时。

**墓碑 domain 扩展（7 → 8）**：新增 `transaction`。

> ⚠️⚠️ `domain` 仍是**硬编码在 6 处**（上表 4 处 + 若干测试锁了精确数组）。
> M3 已经在这一处真实翻过车：白名单漏项让 `meal` / `travel` 的删除
> **读写两条链路一起静默失效、零报错**，直到第 6 步才发现并修掉。
> 本期只加 1 个 domain，反而更容易被当成小事顺手漏掉。
>
> 好消息：`transaction` 的本地删除**可以直接复用 `removeFromPartitioned`**
> —— 那个通用助手要求的接口（`getAll` / `getByDate` / `saveByDate`）
> `LedgerRepository` 全部具备，与饮食 / 运动 / 食谱走同一条通路。

### 3.5 本期最大的改动：老数据导入（数据认领）

这是 M4 与 M2 / M3 最本质的差异：M2 / M3 解决的是「**新**数据怎么上云」，
本期要解决「**已经躺在手机里几个月的数据怎么一次性搬上去**」。

**范围**（对应路线图 §8.3「数据认领」，按本期实际形态细化）：

| 域 | 本机形态 | 云端集合 |
|---|---|---|
| 饮食 / 运动 | 按日期分区 | `diets` / `workouts` |
| 学习计划 / 学习打卡 | 全量单键 / 按日期分区 | `study_plans` / `study_checkins` |
| 食谱 | 按日期分区 | `meal_plans` |
| 出行计划（含明细） | 全量单键（**明细内嵌** `items`） | `travels` + `travel_items` |
| 收支 | 按日期分区 | `transactions`（**本期新建**） |

**流程**

```
① 前置检查：已登录 + 已加入家庭（未满足则按钮直接提示，不产生任何标记）
② 本机读全量：复用 BackupService.export() —— 它已经能拿到上表全部 8 个 domain
③ 归一：prepareImport(payload) → { batches, fixes, total }
     · 补齐 / 校正云端必需形态（note 归成字符串、amount 收敛成有限数、
       members 去重、把 TravelPlan.items 拆成独立的 travelItem 记录 …）
     · 被改动过的字段记进 fixes（用于报数，**不静默改数据**）
④ 分批上行：每批 50 条 → 对应云函数的批量 action
⑤ 汇总报数：成功 / 已在云端 / 失败 + fixes 明细，写入本机导入记录供页面展示
⑥ 此后新增 / 编辑走正常的「本地优先 + markDirty」通路，与导入无关
```

**五条必须成立的性质**

1. **幂等**：云端按 `clientId` 去重，命中计入「已在云端」。所以导入**可以重复点、
   可以失败后整批重跑**，不会产生重复记录 —— 这正是「不需要断点续传协议」的前提；
2. **逐条独立**：一条脏数据不让整批失败，`invalid` 逐条回报（含原因）；
3. **不排待同步标记**：导入是「直连批量写」，全程不落 `pendingSync`。
   否则一次导入会凭空造出几千条标记，`flush()` 要空跑很久（虽然幂等，纯属浪费）；
4. **报数不静默**：本机读取阶段就可能丢数据（`parseStoredArray` 把校验不通过的条目
   **既不返回也不报错**地滤掉，见 §5 第 2 条）。所以导入统计必须以
   「**本机实际能读出的条数**」为基准，并把 `fixes` / `invalid` 摊开给用户看；
5. **可重入**：分批之间有进度提示；某一批失败不影响已成功的批次，重跑即可补齐。

**为什么归一放在前端、云端保持严格**

云端 `importAll` 复用与 `add` **完全相同**的校验器（一套规则，没有「宽松模式」）；
把「历史遗留形态的整理」责任放在前端导入层（纯函数、可穷举单测）。
好处是云端永远只有一套写入规则，而归一逻辑可以被测试穷举覆盖。

### 3.6 三处必须先处理的问题

M3 在动工前先修了 `normalizeItems` 每次重新生成明细 id 这个既有缺陷 —— 本期同样先揭三处。

**① 编辑态改日期必然失败（`record.vue`）—— 纯本地时代就存在**

`save()` 走的是 `ledgerStore.update(date.value, editingId.value, draft)`，
而 `date.value` 会被日期选择器（`onDateChange`）改写。于是「打开一条旧记录 → 改日期 → 保存」
会命中：`LedgerRepository.getByDate(新日期)` 里**找不到这条记录** →
`LedgerService.update` 抛「未找到要编辑的收支记录」→ 界面弹「保存失败」。
删除同理（`remove(date.value, id)`）—— 改过日期之后连删除也会失败。

**处理**：编辑态把日期选择器**置为只读**（新增态可改）。理由见 §2.1 决策 5：
`date` 是分区键与拉取维度，「改日期」在云端是「记录从旧查询通路里消失」的事件；
要支持它就得引入一套移动语义（删旧 + 建新 + 墓碑），而用户的实际诉求是
「这条记错日期了」，删掉重记一次即可。

> 上云之后这个缺陷会更危险：`date` 一旦与本机分区不一致，
> 记录会在**按区间拉取**时凭空消失。

**② 账本备注没有长度上限（`record.vue` 的备注 `<input>`）**

`validateTransaction` 对 `note` 只要求「是字符串」，表单也没有 `:maxlength`。
云端上线后必须有上限（否则超长文本是索引与响应体积的隐患），
而**上限一旦只存在于云端**，就会复现 M2 / M3 反复踩过的那个坑：
用户能输入超长内容 → 本地写入成功（界面一切正常）→ 推云端 400 →
重试 5 次后**丢弃待同步标记** → 记录永久留在本机、云端没有，**全程不报错**。

**处理**：新增 `LEDGER_LIMITS = { note: 100, category: 20 }`（`src/utils/limits.ts`），
三处对齐：**表单 `:maxlength`** ↔ **`ledger/lib.js` 常量** ↔ **schema `maxLength`**，
并按既有做法接入三角闭合守卫（`ui-limits` 锁「前端表 ↔ lib」，
`ledger-schema` 锁「schema ↔ 前端表」，再加「schema 不得比 lib 更严」的方向性断言）。

> ⚠️ **不要给 `validateTransaction` 加长度校验**：本机仓储是「校验不通过即丢弃」，
> 加上限会让**历史里备注超长的整条记录被判非法后静默消失** ——
> 这正是 M3 在 `order` 字段上踩过的同款坑。上限只存在于**表单**（阻止新输入）
> 与**云端**（入参校验）两端。

**③ 「`Transaction` 缺 `clientId`」是个假问题（澄清）**

早先的口头评估里我把「前端模型缺 `clientId`」列成了风险，**实际不成立**：
`clientId` 是**云端字段名**，前端一直用 `id`，两者由映射层换算
（`toCloudTransaction` 里 `clientId: entry.id`），与 `meal` / `travel` 完全一致。
真正需要新增的字段只有云端的 `createdAt` / `updatedAt`，而那是**新集合本来就该有的**。
前端 `Transaction` 模型**一个字段都不用加**，也没有历史数据兼容问题。

## 5. 风险与坑

1. **墓碑 domain 六处硬编码**（§3.4）：M3 真实翻车处；本期只加 1 个值，反而更易漏；
2. **导入的静默丢弃**：本机读取走 `parseStoredArray`，**校验不通过的条目既不返回也不报错**。
   叠加「历史备注超长」「分类不在当前枚举」这类历史遗留，很容易出现
   「导入成功但少了一部分」。所以统计口径必须以**本机可读条数**为基准（§3.5 性质 4）；
3. **归一与云端校验的规则漂移**：归一在前端、校验在云端，两端不一致会出现
   「归一后的数据仍被云端拒」。需要一条**两层串联守卫**：
   `validateTransactionPayload(prepareImport(...).records[i])` 必须全部通过 ——
   这类断言在 M3 的映射层测试里已验证有效；
4. **`memberId` 落空串**（§3.3）：会触发 `optionalIdError` 判非法 → 整条记录被静默丢弃。
   必须用映射层守卫锁死「无值 → `undefined` / `null`，**绝不落 `''`**」；
5. **「`category` 该加白名单」的诱惑**：看着该加，实际会让历史数据导入失败（§3.1）；
6. **导入过程中的并发编辑**：导入处理的是「点按钮那一刻读到的快照」，
   期间用户新记的账走正常通路，两者互不干扰；但**导入期间必须给出进度态**，
   否则用户会以为卡死而反复点击（幂等，不会坏数据，但体验很差）；
7. **UI `maxlength` 缺失**（§3.6 第 2 条）：M2-A / M2-B / M3 都踩过；
8. **账本展示顺序不是时间序**：`LedgerService` 用 `b.id.localeCompare(a.id)` 排序，
   而 `createId` 在支持 `crypto.randomUUID` 的环境（H5）会产出**随机 UUID** ——
   同一天内的先后顺序在 H5 上看起来是随机的（小程序端降级为时间前缀，看起来正常）。
   本期**不改排序口径**（改它会动到所有账本记录的展示顺序，属于体验变更），
   只作为已知限制记录；若真机验收时觉得别扭，单独整改（给 `Transaction` 加可选 `createdAt`）；
9. **金额是浮点数**：`0.1 + 0.2` 类误差沿用现状（前端本来就是 `number` 累加），本期不做定点数；
10. **`list` 单次上限 500 条**：按月区间正常不会触顶；真触顶时**报「拉取被截断」**，不静默少数据。

> **部署后续的设计约束**（由 §2.1 决策 6 推出）：服务空间到期后可能整体迁移，
> 因此本期**不使用支付宝云特有的能力** —— 只用 `uniCloud.database()` 的通用
> `where / orderBy / limit / add / doc(id).update|remove`，schema 只用通用的
> `bsonType / required / permission / maxLength`，不碰任何方言或专用扩展。
> 这样将来迁移只需改服务空间配置并重新上传，业务代码不用动。

## 6. 明确不做

1. 不改 M2 / M3 已有的合并语义与墓碑语义（只做 domain 扩展与新通路）；
2. 不做「预算 ↔ 账本联动」（`budget` 仍在出行计划里，本期不建立关联）；
3. 不做账本图表 / 报表 / 导出 CSV；
4. **不做「改日期（跨分区移动）」** —— 编辑态直接禁用（§2.1 决策 5）；
5. 不做 `sync_meta` 集合（路线图标为「预留，暂未使用」，继续不用）；
6. 不做墓碑自动清理（家庭量级可忽略，M3 也明确不做）；
7. 不做实时推送 —— 仍是「进入页面拉取」；
8. 不做断点续传协议 —— 靠**幂等**支持「失败后整批重跑」（§3.5 性质 1）；
9. 不做「按 domain 选择性导入」—— 一次全导，简单且幂等；
10. 不把「历史超长备注」在导入时截断掉 —— 上限只在表单与云端，导入不做静默裁剪
    （若真出现超长历史数据，走 `invalid` 明确报出来，而不是悄悄改用户的数据）。
