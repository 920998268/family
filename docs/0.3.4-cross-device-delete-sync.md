## 1. 问题：跨设备删除不会同步

### 1.1 现象

> **A 删掉一条饮食 / 运动 / 学习记录后，B 刷新仍然看得到它。**

A 自己那边是正常的（删除是在 A 本地发起的，本地缓存已清）。

### 1.2 根因

两条既有设计叠加的结果：

1. **云端是物理删除** —— `remove` 直接 `db.collection(...).doc(_id).remove()`，
   记录从云端消失，不留任何痕迹；
2. **合并规则刻意保留「本地独有」** —— `utils/checkinMerge.ts` 里
   「云端没有、本地有的记录」一律保留本地版本。

第 2 条本身是**必需的**：它保护「本地新建但还没推上云」的记录不被抹掉
（弱网下最常见）。但第 1 条让「云端已删除」和「从未上云」在 B 端**无法区分** ——
两者都表现为「云端列表里没有这条 id」，于是 B 一律保留。

### 1.3 为什么之前不修

M2-A 的验收标准 2 写的是「A 编辑 / 删除，B 刷新后同步」，
实际只覆盖了**编辑**那一半；删除那一半当时没细测（或 B 端本地恰好没有该条缓存）。

---

## 2. 两个候选方案

### 2.1 方案 C（**否决**）：云端全量覆盖，本地多出来的即删除

把 `pull` 改成「以云端列表为唯一真源，本地有而云端没有的一律删除」。

**否决理由：会在首次 pull 时造成灾难性数据丢失。**

无法区分这三种「本地有、云端没有」：

| # | 情况 | 应如何处理 |
|---|---|---|
| 1 | 本地新建、还没推上云 | **保留**（有 pending 标记，可识别） |
| 2 | 云端被别的设备删了 | **删除**（本次要修的目标） |
| 3 | **老数据从未上云**（M2 明确把老数据导入留到 M4） | **保留** —— 但**没有** pending 标记 |

第 3 类正是致命处：用户设备上可能存着大量 M2 之前的历史本地记录，
它们从未上云、也没有标记。方案 C 会在第一次 pull 时把它们**全部删掉**。

同理，第 4 类「同步失败、重试超限后标记被丢弃」的记录也会被误删。

> 这也解释了为什么「先修『重试超限丢弃标记』」曾被认为是前置条件 ——
> 那个判断是在方案 C 的语境下成立的。**换成墓碑方案后它不再是前置条件**，见 §5.3。

### 2.2 方案 B（**采纳**）：删除日志（墓碑 / tombstone）

删除时在云端**额外写一条删除日志**，其他设备按日志删除本地记录。

**采纳理由**：

- 删除是**显式事件**，只依据明确记录过的事件做删除 → 第 3 类老数据天然安全；
- 不动现有集合的 `list` 语义与 schema，`diets` / `workouts` / `study_*` 一个字段都不用加；
- 可按时间增量拉取（游标），数据量小。

**代价**：多一个集合；三个云函数的 `remove` 都要多写一次库；`study` 的级联删除
要为每个被删打卡补一条墓碑；`checkin-shared` 需要重新上传（本期唯一的公共模块改动）。

## 3. 设计

### 3.1 新集合 `checkin_tombstones`

| 字段 | 类型 | 说明 |
|---|---|---|
| `familyId` | string | 家庭 id（服务端推导，不接受客户端传入） |
| `domain` | string | `diet` / `workout` / `studyPlan` / `studyCheckin` |
| `clientId` | string | 被删记录的幂等键（= 前端记录 id） |
| `date` | string | 被删记录的日期（`YYYY-MM-DD`），学习计划为空串。用于客户端快速定位 |
| `deletedAt` | number | 删除时间（毫秒），**游标依据** |
| `createdByUid` | string | 删除操作人 |

索引：

| 索引名 | 字段 | 唯一 | 用途 |
|---|---|---|---|
| `idx_family_deleted` | `familyId` 升序, `deletedAt` 升序 | 否 | 按家庭 + 游标增量拉取 |

> **不加** `familyId + clientId` 唯一索引：同一 clientId 理论上可能被删多次
> （删除 → 重新添加 → 再删除）。按 `deletedAt` 增量消费即可，不需要去重。

### 3.2 云端 `remove` 的顺序：先删记录，后写墓碑

```
① 查记录（familyId + clientId）
② 若存在 → 物理删除
③ 写墓碑（无论记录是否存在）
④ 返回 { removed: ②是否发生 }
```

**关键：第 ③ 步无论记录是否存在都要执行。**

这样「删除成功但墓碑写入失败」时，客户端重试能补上墓碑 ——
重试时 ② 返回 `removed: false`，但 ③ 照常写，墓碑不会丢。
反过来若「先写墓碑后删记录」，墓碑写了而删除失败 → 其他设备删掉了本地记录，
而 A 下次 pull 时云端记录还在 → **记录复活**（比残留严重得多）。

### 3.3 墓碑的保留期

`listTombstones` 只返回**最近 180 天**的墓碑（`deletedAt > now - 180d`），
上限 500 条。家庭场景下删除量极小，180 天足够覆盖「设备半年不联网」的极端情况。

> 超过 180 天的墓碑不会被自动清理，会累积。家庭场景量级可忽略；
> 若将来需要，可在 `listTombstones` 里加一次惰性清理，或加定时云函数。

### 3.4 客户端：游标增量消费

本地存储键 `family.tombstoneCursor.v1`，记录**已应用到的最大 `deletedAt`**。

1. 读游标 `since`（没有则传 `0` → 拉取全部）；
2. 调三个云函数的 `listTombstones({ since })`；
3. 对每条墓碑：按 `domain` 在本地仓储中定位（`date` 优先，找不到全量兜底）→ 删除；
4. 丢弃该记录对应的 pending 标记（见 §3.5）；
5. 游标推进到本批 `max(deletedAt)`。

### 3.5 冲突处理：**删除优先**

若 B 本地有一条待同步修改（pending 标记）的记录，而墓碑说它已被 A 删除：

> **删除本地记录，并丢弃 pending 标记。**

理由：

- 与既有 `coalesceOp` 的「`remove` 恒胜」约定一致；
- 云端记录已不存在，继续推 `update` 只会 404、重试 5 次后被丢弃，结果一样但白费 5 次；
- 若不丢弃标记，`push` 的 `add` 分支会把记录**重新创建**到云端 →
  A 端又看到它 → 两端来回横跳，比丢一次编辑严重。

代价：B 的离线编辑内容会丢失。这是分布式删除的经典取舍，
本产品设计上取「删除是更强的意图」，行为可预测、可解释。

### 3.6 各 domain 的墓碑归属

| 云函数 | 返回的 domain |
|---|---|
| `diet` | `diet` |
| `workout` | `workout` |
| `study` | `studyPlan` **+ `studyCheckin`**（主从同函数，一次返回两类） |

`study` 的 `removePlan` 级联删打卡时，**必须为每一个被删的打卡补一条墓碑** ——
否则 B 端会出现「计划没了但打卡还在」的孤儿打卡。

## 4. 出口验收标准

1. A 删除一条饮食记录 → B 重新进入饮食页，该记录消失；
2. A 删除一条运动记录 → B 同步消失；
3. A 删除一个学习计划 → B 的**计划与其全部打卡**一并消失（级联墓碑生效）；
4. A 删除某天的一条学习打卡 → B 同步消失；
5. **删除不误伤本地老数据**：设备上「从未上云的本地历史记录」仍在（墓碑里没有它们的 id）；
6. **删除不误伤离线新增**：B 离线新增一条（未上云），此时 A 删除别的一条 →
   B 联网后，自己新增的那条**仍在**，A 删的那条消失；
7. 幂等：同一条墓碑被重复拉取并应用，不报错、不产生副作用；
8. 删除优先：B 有一条待同步编辑的记录被 A 删除 → B 端该记录消失，且待同步标记被清
   （不会反复重投）。

## 5. 明确不做

### 5.1 历史已删除的数据不补

墓碑是**从整改部署生效之日起**才开始写的。在此之前被删除的记录没有墓碑，
它们在 B 端的残留**不会被追溯清理**。

> 若某台设备上残留着「云端早已删除」的旧记录，需要用户在本机手动删除一次。
> 这是可接受的：那些记录本来就在用户自己的设备上、用户随时能删。

### 5.2 不做墓碑的定时清理

见 §3.3，180 天窗口 + 惰性累积足够。

### 5.3 不改「重试超限丢弃标记」策略

先前判断「必须先修它」，是在方案 C（全量覆盖）的语境下成立的 ——
因为那样会把「同步失败但本地还在」的记录误删。

**采用墓碑方案后它不再是前置条件**：删除只依据墓碑事件，
与某条记录有没有 pending 标记无关（§3.5 的「删除优先」是另一回事，
它处理的是「有标记且被删」，而不是「无标记」）。

该策略本身仍有改进价值（标记被丢弃后记录永远上不了云），
但属于独立的课题，不阻塞本次整改。
