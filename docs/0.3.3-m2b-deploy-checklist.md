| 文件 | 对应集合 |
|---|---|
| `uniCloud-alipay/database/study_plans.schema.json` | `study_plans` |
| `uniCloud-alipay/database/study_checkins.schema.json` | `study_checkins` |

> 两个 schema 的 `permission` **全部为 false**：客户端不能直连数据库，只能走云函数。

### 2.2 上传 `study` 云函数 ⬜

右键 `uniCloud-alipay/cloudfunctions/study` →「**上传部署**」。

> ⚠️ 这个函数不在 `diet` / `workout` 里：学习计划与学习打卡是**主从关系**
> （打卡要校验计划存在、删计划要级联删打卡），所以合并成一个函数。
> 理由详见方案 §2.1。

### 2.3 建 5 条索引 ⬜

> 项目里没有 `db_init.json`，uniCloud 的 db-schema 也**不支持声明索引**，
> 所以索引只能在控制台手工建（与云函数、schema 一样属于「必须手工做」的部分）。

#### 入口

uniCloud web 控制台 →「**云数据库**」→ 左侧选中集合 →「**索引管理**」标签 →「**新建索引**」。

> 最省事的打开方式：在 HBuilderX 里右键 `uniCloud-alipay` 目录 →
> 「**打开 uniCloud web 控制台**」，会自动带上当前服务空间。

#### 逐条填写参数

每条索引填「索引名 + 字段（可多个，各自选升序/降序）+ 是否唯一」：

| 集合 | 索引名（建议） | 字段与排序 | 唯一 |
|---|---|---|---|
| `study_plans` | `idx_family_client` | `familyId` 升序, `clientId` 升序 | ✅ **是** |
| `study_plans` | `idx_family_created` | `familyId` 升序, `createdAt` **降序** | 否 |
| `study_checkins` | `idx_family_client` | `familyId` 升序, `clientId` 升序 | ✅ **是** |
| `study_checkins` | `idx_family_date` | `familyId` 升序, `date` 升序 | 否 |
| `study_checkins` | `idx_family_plan_date` | `familyId` 升序, `planId` 升序, `date` 升序 | ✅ **是** |

**每条的用途**：

- `familyId + clientId`（两个集合各一条）—— **幂等写入的唯一键**。
  弱网重投、离线队列重发都靠它挡住重复记录；
- `familyId + createdAt` —— 计划列表按创建时间倒序展示（`orderBy('createdAt', 'desc')`）；
- `familyId + date` —— 打卡是按日期拉的，最高频的查询路径；
- `familyId + planId + date` —— **保证「同一计划同一天只打卡一次」**。

> 最后一条是本期的**实质收益**：本地只能靠应用层校验（`StudyService` 里的
> 「该计划今天已打卡」），两台设备同时点会重复；唯一索引把这条规则下沉到数据库层。

#### 三个容易出错的点

1. **复合索引的字段顺序不能颠倒**：所有查询都带 `familyId`，所以它**必须放第一位**。
   顺序错了索引就用不上（查询会退化成全表扫描），而且**不会报错**，很难发现。
2. **建唯一索引前，表里不能已有重复值**。`study_plans` / `study_checkins` 是本期新建的
   空集合，正常不会有问题；但如果你手动插过测试数据，请先删掉重复项再建，
   否则创建会失败（报重复键）。
3. **索引建好立即生效，不需要重新上传云函数**；反过来，删掉唯一索引也不会报错，
   但会**悄悄失去幂等保护** —— 别为了「让写入先跑通」去删它。

#### 怎么确认建对了

「索引管理」列表里应当能看到 5 条，且 3 条带「唯一」标记。
建完后可以顺手在「数据查询」里手动插入一条重复的 `familyId + clientId` 记录，
**预期被拒绝** —— 能拒绝就说明唯一索引真的生效了。

## 5. ⚠️ 已知缺口：跨设备删除不会同步

**请在上面 §4.3 的用例之外单独了解这一点**，它是**既有行为**（M2-A 的饮食 / 运动同样如此），
不是本期引入的回归：

`utils/checkinMerge.ts` 的合并规则刻意**保留「云端已删除但本地仍在」的记录**，
且没有独立的删除传播机制。所以：

> **A 删掉一个学习计划后，B 刷新仍然看得到它。**
> （A 自己那边是正常的，因为删除是在 A 本地发起的。）

M2-A 的验收标准 2（「A 编辑 / 删除，B 刷新后同步」）实际只覆盖了**编辑**那一半。

**什么时候会修**：它涉及共享的 merge 语义（diet / workout / study 三处都受影响），
且必须先解决一个前置问题 —— 现在的规则下，一条「推了 5 次都失败、标记被丢弃」的记录
会变成「本地有、云端没有、也没标记」，若直接改成「本地独有即视为云端已删」，
会把这条**同步失败但用户数据还在**的记录误删成永久丢失。
所以需要连同「重试超限后不再丢弃标记」一起改。

`tests/study-sync.test.ts` 里有一条标了 🔴 的测试把这个行为**显式固定**，
避免以后误以为已经支持。

## 6. 故障排查（增补）

M2-A 清单 §7 的三节仍然适用，本期补充：

| 现象 | 排查 |
|---|---|
| 学习打卡不上云，但界面一切正常 | 按 M2-A 清单 §7.3 的两步法：先看 Local Storage 里有没有 `uni_id_token`，再看 `family.pendingSync.v1` 的 `attempts` 与 `lastError`。**注意本期新增了两个 domain**：`studyPlan` 与 `studyCheckin`，标记里的 `domain` 字段可用来判断是哪一类 |
| `未知操作: xxx` | `study` 云函数是旧版本，重新上传部署 |
| 删除计划时报「该计划的历史打卡较多，本次未清理完」 | 这是**设计行为**：服务端不会带着未删完的打卡删计划（否则留下孤儿）。**重试即可** —— 每轮删除都有进展，重试几次就会删完 |
| 同一天给同一计划打卡报错 | 正常，服务端会返回 `duplicated` 而不是报错；若界面报错说明前端版本过旧 |
