## 2. 云端部署（HBuilderX，需手工操作）

### 2.0 路径速查（先把「哪个是哪个」分清）

本次要上传的 **6 个条目**（只有一个云空间目录 `uniCloud-alipay/`，不存在传错平台的问题）：

| # | 完整路径 | 类型 | 右键菜单 |
|---|---|---|---|
| 1 | `uniCloud-alipay/database/diets.schema.json` | 文件 | 上传 DB Schema |
| 2 | `uniCloud-alipay/database/workouts.schema.json` | 文件 | 上传 DB Schema |
| 3 | `uniCloud-alipay/database/favorite_foods.schema.json` | 文件 | 上传 DB Schema |
| 4 | `uniCloud-alipay/cloudfunctions/common/checkin-shared` | 目录 | 上传公共模块 |
| 5 | `uniCloud-alipay/cloudfunctions/diet` | 目录 | 上传部署 |
| 6 | `uniCloud-alipay/cloudfunctions/workout` | 目录 | 上传部署 |

#### 四处最容易混的地方

1. **云函数目录是单数，集合 / schema 是复数**，它们是一一配对的：

   | 云函数（单数） | 集合 / schema（复数） |
   |---|---|
   | `uniCloud-alipay/cloudfunctions/diet` | `diets` / `uniCloud-alipay/database/diets.schema.json` |
   | `uniCloud-alipay/cloudfunctions/workout` | `workouts` / `uniCloud-alipay/database/workouts.schema.json` |

2. **`favorite_foods` 没有自己的云函数** —— 它由 `diet` 云函数托管。
   所以是「**3 个 schema 对应 2 个云函数**」，不要去找 `favorite_foods` 云函数。

3. **`common/` 下有 7 个模块，只有 1 个是本项目的**。
   判别方法：去 `src/uni_modules/` 找同名来源 —— **有来源的都是第三方**（HBuilderX 自动拷贝的副本）：

   | 模块 | 来源 | 本次 |
   |---|---|---|
   | `uniCloud-alipay/cloudfunctions/common/checkin-shared` | **无**（本仓库自研） | ✅ 上传 |
   | `uniCloud-alipay/cloudfunctions/common/uni-id-common` | `src/uni_modules/uni-id-common` | ❌ 不动 |
   | `uniCloud-alipay/cloudfunctions/common/uni-config-center` | `src/uni_modules/uni-config-center` | ❌ 不动 |
   | `uniCloud-alipay/cloudfunctions/common/uni-captcha` | `src/uni_modules/uni-captcha` | ❌ 不动 |
   | `uniCloud-alipay/cloudfunctions/common/uni-cloud-s2s` | `src/uni_modules/uni-cloud-s2s` | ❌ 不动 |
   | `uniCloud-alipay/cloudfunctions/common/uni-open-bridge-common` | `src/uni_modules/uni-open-bridge-common` | ❌ 不动 |
   | `uniCloud-alipay/cloudfunctions/common/x-uni-id-co` | `src/uni_modules/x-uni-id-co` | ❌ 不动 |

4. **`database/` 下有 5 个 schema，本次只需传 3 个**：
   `uniCloud-alipay/database/families.schema.json` 与
   `uniCloud-alipay/database/family_members.schema.json` 属于 M0/M1，此前已部署（重传也不会坏，但没必要）。
   `JQL查询.jql` 是控制台查询片段，不是部署项。

> `cloudfunctions/` 下其余目录（`family` / `member` / `register` / `uni-id-co` / `uni-captcha-co`）
> 都属于早前版本，本次不动。

### 2.1 上传 3 个 DB Schema ⬜

在 HBuilderX 中：

1. 展开 `uniCloud-alipay` → 右键 `database` 目录；
2. 选择「**上传 DB Schema**」（若菜单无此项，逐个右键 schema 文件上传）；
3. 确认要上传的文件：

| 文件 | 对应集合 | 说明 |
|---|---|---|
| `uniCloud-alipay/database/diets.schema.json` | `diets` | 饮食记录 |
| `uniCloud-alipay/database/workouts.schema.json` | `workouts` | 运动记录（力量 / 有氧共用） |
| `uniCloud-alipay/database/favorite_foods.schema.json` | `favorite_foods` | 常用食物（随打卡自动沉淀） |

4. 上传后到 uniCloud 控制台「云数据库」确认 3 个集合出现。

> 三个 schema 的 `permission` **全部为 false**：客户端不能直连数据库，只能走云函数。
> 这是刻意的安全设计，不要为了「方便调试」放开。

### 2.2 上传公共模块 `checkin-shared` ⬜

1. 右键 `uniCloud-alipay/cloudfunctions/common/checkin-shared` → 「**上传公共模块**」；
2. 确认控制台显示上传成功。

> ⚠️ **最容易漏的一步**。`diet` / `workout` 都 `require('checkin-shared')`
> （登录态校验 + 家庭归属推导）。不传这个模块，两个云函数都跑不起来。

### 2.3 上传 `diet` 云函数 ⬜

右键 `uniCloud-alipay/cloudfunctions/diet` → 「**上传部署**」。

### 2.4 上传 `workout` 云函数 ⬜

右键 `uniCloud-alipay/cloudfunctions/workout` → 「**上传部署**」。

> ### ⛔ 不要用「上传所有云函数、公共模块及 actions」
>
> 该操作会**连带重传 `uni-config-center`**。而 `src/uni_modules/uni-config-center/`
> （HBuilderX 的公共模块来源目录）里**没有** `uni-id/config.json` ——
> 它是一份手工放置的本地配置。重传后云端的 uni-id 配置会丢失，
> 导致**所有登录/注册接口报 `Invalid uni-id config file`**（2026-09-12 实际踩过一次）。
>
> 只逐个上传 2.2 / 2.3 / 2.4 这三个，别图省事。

### 2.5 建索引 ⬜

到 uniCloud 控制台「云数据库」→ 选中集合 →「索引管理」→ 新建：

| 集合 | 索引字段 | 类型 | 为什么必须 |
|---|---|---|---|
| `diets` | `familyId` + `date` | 复合（非唯一） | 列表按家庭 + 日期查询，是最高频路径 |
| `diets` | `familyId` + `clientId` | 复合（**唯一**） | 幂等写入的唯一键；不设唯一索引，弱网重投会产生重复记录 |
| `workouts` | `familyId` + `date` | 复合（非唯一） | 同上 |
| `workouts` | `familyId` + `clientId` | 复合（**唯一**） | 同上 |
| `favorite_foods` | `familyId` + `name` | 复合（**唯一**） | 常用食物按家庭内名称唯一；不设则同一食物会沉淀出多条 |

> 唯一索引同时也是**兜底防线**：即使前端的幂等逻辑出问题，数据库层也会挡住重复写入。

> **验证分三层，从快到慢**：2.6 云端自检（不用手机，约 1 分钟）→ 2.7 H5 端到端
> （不用手机，约 10 分钟，能覆盖 5 条出口验收标准里的 4 条）→ §4 真机 + §5 双端。

### 2.6 第一层：云端自检 ⬜

**① 3 个集合是否建好** → 控制台「云数据库」，应能看到 `diets` / `workouts` / `favorite_foods`。

**② 5 条索引是否建好** → 每个集合的「索引管理」页逐条核对（见 2.5 的表）。

**③ 云函数是否可用** —— 两种方式任选其一：

#### 方式 A：浏览器 Console 直接调用（推荐，零控制台依赖）

打开 H5（`npm run dev:h5`）→ F12 → Console，粘贴：

```js
uniCloud.callFunction({ name: 'diet',    data: { action: 'list', date: '2026-09-12' } }).then(r => console.log('diet   ', r.result))
uniCloud.callFunction({ name: 'workout', data: { action: 'list', date: '2026-09-12' } }).then(r => console.log('workout', r.result))
```

`uniCloud` 挂在 `window` 上（由 `initUniCloud()` 在 `onLaunch` 里注入），直接可用。
这种方式走的是**真实客户端链路**（含自动携带的 `uniIdToken`），比控制台测试更接近实际。

#### 方式 B：控制台「云端测试」

部分控制台版本 / 服务空间没有这个按钮，入口名也可能叫「测试」或在函数详情页内。
**找不到就用方式 A**，两者返回一致。

> 另外：`uni-id-co` / `uni-captcha-co` 是**云对象**，不在「云函数」列表里，
> 它们在控制台的「云对象」分类下。

于是得到以下结果，对照下表判断：

```json
{ "action": "list", "date": "2026-09-12" }
```

| 返回 | 含义 | 处理 |
|---|---|---|
| `{"code":0,"data":[...]}` | ✅ **全链路正常**，且已读到记录 | 进入 2.7 |
| `{"code":0,"data":[]}` | ✅ 全链路正常，只是当天没数据 | 进入 2.7 |
| `{"code":401,"msg":"登录态无效或已过期"}` | ✅ **部署正常**（见下方说明） | 先登录再重试 |
| `{"code":400,"msg":"尚未加入家庭"}` | ✅ 鉴权通过，只是账号未加入家庭 | 正常 |
| `{"code":400,"msg":"未知操作: undefined"}` | ✅ 路由正常（没传 action 时的兜底） | 正常 |
| `Cannot find module 'checkin-shared'` | ❌ 公共模块没传成功 | 回到 2.2 重传 |
| `集合不存在` / `collection not exists` | ❌ schema 没传成功 | 回到 2.1 重传 |
| 超时 / 500 | ❌ 云函数有语法或运行时错误 | 看该函数的「日志」里的报错栈 |

**为什么 401 是好消息**：`diet` 的 `require('checkin-shared')` 写在模块顶层，
公共模块没传成功时函数**根本加载不起来**，报的是模块找不到而不是 401。
能返回结构化的 401，说明云函数已部署 + 公共模块已解析 + 鉴权链路生效。

> ⚠️ 但 401 **不能证明 `uni-id-common` 也是好的**：`getUid()` 里
> `require('uni-id-common')` 被 `try/catch` 包着，模块缺失会被兜成同一个 401。
> 它是 M0/M1 就在用的老模块，基本不会出问题；真要确认请走 2.7。

`workout` 请用同样方式再测一遍。

### 2.7 第二层：H5 端到端（不用手机，性价比最高）⬜

H5 支持**手机号 + 密码**登录，所以在一台电脑上开两个浏览器窗口，
就能把「双端可见」验证掉 —— 5 条出口验收标准里 4 条不碰手机即可确认。

1. `npm run dev:h5` → 打开 `http://localhost:5173`；
2. 用**已加入家庭**的手机号 + 密码登录；
3. **先做这一步检查（最关键）**：F12 → Application → Local Storage，
   确认存在 `uni_id_token`。

   > ⚠️ 这个键没有任何前端代码显式写入，它由 uni-id-co 的客户端机制持久化。
   > **若它不存在，`isCheckinCloudReady()` 会判定为未登录，所有云调用被静默跳过**
   > ——现象就是「打卡一切正常、但云端一条数据都没有、也不报错」。
   > 这是「数据没上云」最常见也最隐蔽的成因，务必先排除。

4. 进入「打卡 → 饮食」，新增一条（如：午餐 / 鸡胸肉 / 200g）；
5. 回到 Local Storage 观察：
   - `family.diet.v1.<日期>` 有值 → 本地缓存已写入；
   - **`family.pendingSync.v1` 在几秒内消失** → 说明已成功推上云；
     **若它一直存在** → 上传失败，值里会带 `lastError` 写明原因；
6. 切到 uniCloud 控制台 →「云数据库」→ `diets`，应出现一条新文档，形态如下：

```json
{
  "_id": "服务端生成",
  "familyId": "你的家庭 id",
  "clientId": "diet-xxxxxxxx-xxxx-...",
  "date": "2026-09-12",
  "mealType": "lunch",
  "foodName": "鸡胸肉",
  "quantity": "200g",
  "calories": null, "protein": null, "carbs": null, "fat": null,
  "memberId": null,
  "createdByUid": "你的 uid",
  "createdAt": 1789000000000,
  "updatedAt": 1789000000000
}
```

同时 `favorite_foods` 会自动沉淀一条 `鸡胸肉`（`useCount: 1`）。

运动记录（有氧）则应是：

```json
{
  "category": "cardio",
  "exerciseName": "跑步",
  "sets": [],
  "durationMin": 30,
  "distanceKm": 5.2,
  "calories": null,
  "...": "其余字段同上"
}
```

> 有氧记录 `sets` 必须是**空数组**；力量记录 `sets` 必须有元素且 `order` 从 1 连续。
> 若看到力量记录 `sets: []` 或有氧记录带组明细，说明表单或校验有问题。

7. **双端可见**（对应验收标准 1 / 2）：另开一个**隐身窗口**，用同一家庭**另一个账号**登录，
   进打卡页 → 应看到刚新增的那条；编辑 / 删除后再回隐身窗口刷新，应同步；
8. **离线补传**（对应验收标准 3）：F12 → Network → 切 `Offline` → 再新增一条 →
   列表仍立即出现（本地优先），此时 `family.pendingSync.v1` **存在**且含一条 `"op":"add"`；
   切回 `Online` → 重新进入打卡页 → 该键消失、控制台 `diets` 多一条。

**H5 覆盖不到、必须真机的部分**：微信登录、微信 request 合法域名、真机弱网表现、
以及「两人同时写」的真实并发。这些按 §4 的 25 条用例走真机，
重点是**用例 18（离线编辑不被云端旧值覆盖）、19（同时新增都保留）、21（历史老记录不丢）**。

## 4. 第三层：真机验收用例

> 前置：两个微信号（A / B）登录后进入**同一个家庭**；两台设备或一台设备两个微信号切换。
> 判定标准来自方案 §1.2「出口验收标准」。
> 建议先跑完 2.6 / 2.7 —— 云端与链路问题在 H5 阶段就能暴露，别留到真机上排查。

### 4.1 基础链路（单人）

| # | 用例 | 操作 | 预期 | 状态 |
|---|---|---|---|---|
| 1 | 新增饮食 | 打卡 → 饮食 → 新增 → 保存 | 列表立即出现；**不转圈等待网络** | ⬜ |
| 2 | 修改饮食 | 编辑数量后保存 | 列表立即更新 | ⬜ |
| 3 | 删除饮食 | 删除某条 | 列表立即移除 | ⬜ |
| 4 | 新增力量训练 | 打卡 → 运动 → 类型「力量」→ 动作 + 组明细 → 保存 | 列表显示「力量 · N 组 · 60kg × 8 / ...」 | ⬜ |
| 5 | 新增有氧训练 | 类型切「有氧」→ 项目名「跑步」+ 时长 30 + 距离 5.2 → 保存 | 列表显示「有氧 · 30 分钟 · 5.2 公里」 | ⬜ |
| 6 | 有氧时长必填 | 有氧只填项目名就保存 | 提示「请填写运动时长（分钟）」，不保存 | ⬜ |
| 7 | 类型切换 | 编辑一条力量记录，切到「有氧」并填时长后保存 | 保存成功，列表按「有氧」展示且不再显示组明细 | ⬜ |
| 8 | 常用食物 | 新增饮食 → 点「常用」 | 展开面板；此前打卡过的食物按使用次数降序出现 | ⬜ |
| 9 | 一键带出 | 点某个常用食物 | 名称 / 数量 / 营养值被自动填入 | ⬜ |
| 10 | 删除常用食物 | 常用面板里点某条「删除」 | 该条从列表消失；下次不再出现 | ⬜ |

### 4.2 双端可见（核心验收）

| # | 用例 | 操作 | 预期 | 状态 |
|---|---|---|---|---|
| 11 | A 写 B 可见 | A 新增一条饮食 → **B 退出再进入打卡页** | B 能看到 A 的记录 | ⬜ |
| 12 | A 改 B 同步 | A 编辑该条 → B 重新进入页面 | B 看到修改后的内容 | ⬜ |
| 13 | A 删 B 同步 | A 删除该条 → B 重新进入页面 | B 侧该条消失 | ⬜ |
| 14 | 运动同样双端可见 | 用有氧记录重做 11~13 | 同饮食 | ⬜ |

> 「进入页面拉取」是本期的同步方式（无实时推送）。B 必须**重新进入页面**才看到变化。

### 4.3 离线与并发（最容易出问题的部分）

| # | 用例 | 操作 | 预期 | 状态 |
|---|---|---|---|---|
| 15 | 断网打卡 | 开飞行模式 → 新增一条饮食 | 保存成功且列表立即出现（本地优先） | ⬜ |
| 16 | 恢复网络补传 | 关飞行模式 → 重新进入打卡页 | 刚才那条**自动补传**到云端 | ⬜ |
| 17 | 补传后双端一致 | 用 B 端验证 16 的结果 | B 能看到断网期间那条记录 | ⬜ |

## 7. 故障排查（按报错原文索引）

### 7.1 `Invalid uni-id config file`

**完整报错**（出现在登录 / 注册 / 任何 `uni-id-co` 调用）：

```
[env-xxxx][uni-id-co][uuid] User Function Code Logic Error
{"code":"400","message":"error: Invalid uni-id config file
  at x._getOriginConfig (@common_modules/uni-id-common/index.js)"}
```

**根因**：云端 `common/uni-config-center/uni-id/config.json` **不存在**。

**证据链**（来自 `uni-id-common` 的实际代码）：

```js
if (w.hasFile('config.json')) { ... }                    // ① 文件在 → 正常读取
try { return require('uni-id/config.json') }             // ② 文件不在 → 兜底
catch (e) { throw new Error('Invalid uni-id config file') }  // ③ 兜底也失败 → 就是这句
```

报错文本**没有**附加 `"\n" + e.message`，说明走的是分支 ③：
`uni-config-center` 里没有 `uni-id/config.json`，云函数的 `node_modules` 里也没有。

**关于配置文件的路径**（容易放错）：插件用
`path.resolve(__dirname, pluginId)` 定位，即
`uniCloud-alipay/cloudfunctions/common/uni-config-center/uni-id/config.json` —— **顶层那份**。

> ⚠️ 本仓库在 `uni-config-center/` 下还有一份**嵌套副本**
> `uniCloud/cloudfunctions/common/uni-config-center/uni-id/config.json`。
> **插件不读它**，放在那里等于没放。

**修复步骤**：

1. HBuilderX 中右键 `uniCloud-alipay/cloudfunctions/common/uni-config-center` →「上传公共模块」；
2. 上传后到 uniCloud 控制台「云函数」→「公共模块」，确认 `uni-config-center` 下有 `uni-id/config.json`；
3. 重新用微信或手机号登录验证。

**防复发**：以后**不要**用 2.4 提到的「上传所有云函数、公共模块及 actions」。

### 7.2 本地存在两份 uni-id 配置，只有顶层那份有效

排查时发现本地有两份 `config.json`：

| 位置 | 是否被读取 |
|---|---|
| `common/uni-config-center/uni-id/config.json` | ✅ **插件读这份**（`path.resolve(__dirname, 'uni-id')`） |
| `common/uni-config-center/uniCloud/cloudfunctions/common/uni-config-center/uni-id/config.json` | ❌ 不读，放着等于没放 |

两份的**唯一差异**是 `loginTypes`（`["weixin"]` vs `["weixin","username"]`）。

> 已核实：`loginTypes` 在**全部 147 个公共模块 JS 文件里一次都没出现** ——
> 服务端不校验该字段，所以这个差异是**良性的**，不会导致手机号登录/注册失败。
> 不必为此改动配置。

**结论**：只要顶层那份 `common/uni-config-center/uni-id/config.json` 存在且是合法 JSON 即可。
嵌套那份属于放错位置，建议删掉以免日后误导（注意：这两份都在 `.gitignore` 里，不会进版本库）。
