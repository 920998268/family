## 2. 云端部署（HBuilderX，需手工操作）

### 2.0 路径速查（先把「哪个是哪个」分清）

本次要上传的 **6 个条目**（只有一个云空间目录 `uniCloud-alipay/`，不存在传错平台的问题）：

| # | 完整路径 | 类型 | 右键菜单 |
|---|---|---|---|
| 1 | `uniCloud-alipay/database/diets.schema.json` | 文件 | 上传 DB Schema |
| 2 | `uniCloud-alipay/database/workouts.schema.json` | 文件 | 上传 DB Schema |
| 3 | `uniCloud-alipay/database/favorite_foods.schema.json` | 文件 | 上传 DB Schema |
| 4 | `uniCloud-alipay/cloudfunctions/common/checkin-shared` | 目录 | 上传公共模块 |
| 5 | `uniCloud-alipay/cloudfunctions/diet` | 目录 | 上传部署 |
| 6 | `uniCloud-alipay/cloudfunctions/workout` | 目录 | 上传部署 |

#### 四处最容易混的地方

1. **云函数目录是单数，集合 / schema 是复数**，它们是一一配对的：

   | 云函数（单数） | 集合 / schema（复数） |
   |---|---|
   | `uniCloud-alipay/cloudfunctions/diet` | `diets` / `uniCloud-alipay/database/diets.schema.json` |
   | `uniCloud-alipay/cloudfunctions/workout` | `workouts` / `uniCloud-alipay/database/workouts.schema.json` |

2. **`favorite_foods` 没有自己的云函数** —— 它由 `diet` 云函数托管。
   所以是「**3 个 schema 对应 2 个云函数**」，不要去找 `favorite_foods` 云函数。

3. **`common/` 下有 7 个模块，只有 1 个是本项目的**。
   判别方法：去 `src/uni_modules/` 找同名来源 —— **有来源的都是第三方**（HBuilderX 自动拷贝的副本）：

   | 模块 | 来源 | 本次 |
   |---|---|---|
   | `uniCloud-alipay/cloudfunctions/common/checkin-shared` | **无**（本仓库自研） | ✅ 上传 |
   | `uniCloud-alipay/cloudfunctions/common/uni-id-common` | `src/uni_modules/uni-id-common` | ❌ 不动 |
   | `uniCloud-alipay/cloudfunctions/common/uni-config-center` | `src/uni_modules/uni-config-center` | ❌ 不动 |
   | `uniCloud-alipay/cloudfunctions/common/uni-captcha` | `src/uni_modules/uni-captcha` | ❌ 不动 |
   | `uniCloud-alipay/cloudfunctions/common/uni-cloud-s2s` | `src/uni_modules/uni-cloud-s2s` | ❌ 不动 |
   | `uniCloud-alipay/cloudfunctions/common/uni-open-bridge-common` | `src/uni_modules/uni-open-bridge-common` | ❌ 不动 |
   | `uniCloud-alipay/cloudfunctions/common/x-uni-id-co` | `src/uni_modules/x-uni-id-co` | ❌ 不动 |

4. **`database/` 下有 5 个 schema，本次只需传 3 个**：
   `uniCloud-alipay/database/families.schema.json` 与
   `uniCloud-alipay/database/family_members.schema.json` 属于 M0/M1，此前已部署（重传也不会坏，但没必要）。
   `JQL查询.jql` 是控制台查询片段，不是部署项。

> `cloudfunctions/` 下其余目录（`family` / `member` / `register` / `uni-id-co` / `uni-captcha-co`）
> 都属于早前版本，本次不动。

### 2.1 上传 3 个 DB Schema ⬜

在 HBuilderX 中：

1. 展开 `uniCloud-alipay` → 右键 `database` 目录；
2. 选择「**上传 DB Schema**」（若菜单无此项，逐个右键 schema 文件上传）；
3. 确认要上传的文件：

| 文件 | 对应集合 | 说明 |
|---|---|---|
| `uniCloud-alipay/database/diets.schema.json` | `diets` | 饮食记录 |
| `uniCloud-alipay/database/workouts.schema.json` | `workouts` | 运动记录（力量 / 有氧共用） |
| `uniCloud-alipay/database/favorite_foods.schema.json` | `favorite_foods` | 常用食物（随打卡自动沉淀） |

4. 上传后到 uniCloud 控制台「云数据库」确认 3 个集合出现。

> 三个 schema 的 `permission` **全部为 false**：客户端不能直连数据库，只能走云函数。
> 这是刻意的安全设计，不要为了「方便调试」放开。

### 2.2 上传公共模块 `checkin-shared` ⬜

1. 右键 `uniCloud-alipay/cloudfunctions/common/checkin-shared` → 「**上传公共模块**」；
2. 确认控制台显示上传成功。

> ⚠️ **最容易漏的一步**。`diet` / `workout` 都 `require('checkin-shared')`
> （登录态校验 + 家庭归属推导）。不传这个模块，两个云函数都跑不起来。

### 2.3 上传 `diet` 云函数 ⬜

右键 `uniCloud-alipay/cloudfunctions/diet` → 「**上传部署**」。

### 2.4 上传 `workout` 云函数 ⬜

右键 `uniCloud-alipay/cloudfunctions/workout` → 「**上传部署**」。

> **省事做法**：右键 `cloudfunctions` 目录 → 「上传所有云函数、公共模块及 actions」，
> 一次把 2.2 / 2.3 / 2.4 都做掉（代价是会连带重传 `family` / `member` / `register`）。

### 2.5 建索引 ⬜

到 uniCloud 控制台「云数据库」→ 选中集合 →「索引管理」→ 新建：

| 集合 | 索引字段 | 类型 | 为什么必须 |
|---|---|---|---|
| `diets` | `familyId` + `date` | 复合（非唯一） | 列表按家庭 + 日期查询，是最高频路径 |
| `diets` | `familyId` + `clientId` | 复合（**唯一**） | 幂等写入的唯一键；不设唯一索引，弱网重投会产生重复记录 |
| `workouts` | `familyId` + `date` | 复合（非唯一） | 同上 |
| `workouts` | `familyId` + `clientId` | 复合（**唯一**） | 同上 |
| `favorite_foods` | `familyId` + `name` | 复合（**唯一**） | 常用食物按家庭内名称唯一；不设则同一食物会沉淀出多条 |

> 唯一索引同时也是**兜底防线**：即使前端的幂等逻辑出问题，数据库层也会挡住重复写入。

### 2.6 部署后自检 ⬜

在 uniCloud 控制台「云函数」→ 选择 `diet` → 「云端测试」，用以下参数调用：

```json
{ "action": "list", "date": "2026-09-12" }
```

| 返回 | 含义 | 处理 |
|---|---|---|
| `{"code":401,...}` 或登录态相关提示 | 云函数已跑通，只是测试环境无 token | 正常，进入第 4 节真机验收 |
| `Cannot find module 'checkin-shared'` | 公共模块没传成功 | 回到 2.2 重传 |
| `集合不存在` / `collection not exists` | schema 没传成功 | 回到 2.1 重传 |

## 4. 真机验收用例

> 前置：两个微信号（A / B）登录后进入**同一个家庭**；两台设备或一台设备两个微信号切换。
> 判定标准来自方案 §1.2「出口验收标准」。

### 4.1 基础链路（单人）

| # | 用例 | 操作 | 预期 | 状态 |
|---|---|---|---|---|
| 1 | 新增饮食 | 打卡 → 饮食 → 新增 → 保存 | 列表立即出现；**不转圈等待网络** | ⬜ |
| 2 | 修改饮食 | 编辑数量后保存 | 列表立即更新 | ⬜ |
| 3 | 删除饮食 | 删除某条 | 列表立即移除 | ⬜ |
| 4 | 新增力量训练 | 打卡 → 运动 → 类型「力量」→ 动作 + 组明细 → 保存 | 列表显示「力量 · N 组 · 60kg × 8 / ...」 | ⬜ |
| 5 | 新增有氧训练 | 类型切「有氧」→ 项目名「跑步」+ 时长 30 + 距离 5.2 → 保存 | 列表显示「有氧 · 30 分钟 · 5.2 公里」 | ⬜ |
| 6 | 有氧时长必填 | 有氧只填项目名就保存 | 提示「请填写运动时长（分钟）」，不保存 | ⬜ |
| 7 | 类型切换 | 编辑一条力量记录，切到「有氧」并填时长后保存 | 保存成功，列表按「有氧」展示且不再显示组明细 | ⬜ |
| 8 | 常用食物 | 新增饮食 → 点「常用」 | 展开面板；此前打卡过的食物按使用次数降序出现 | ⬜ |
| 9 | 一键带出 | 点某个常用食物 | 名称 / 数量 / 营养值被自动填入 | ⬜ |
| 10 | 删除常用食物 | 常用面板里点某条「删除」 | 该条从列表消失；下次不再出现 | ⬜ |

### 4.2 双端可见（核心验收）

| # | 用例 | 操作 | 预期 | 状态 |
|---|---|---|---|---|
| 11 | A 写 B 可见 | A 新增一条饮食 → **B 退出再进入打卡页** | B 能看到 A 的记录 | ⬜ |
| 12 | A 改 B 同步 | A 编辑该条 → B 重新进入页面 | B 看到修改后的内容 | ⬜ |
| 13 | A 删 B 同步 | A 删除该条 → B 重新进入页面 | B 侧该条消失 | ⬜ |
| 14 | 运动同样双端可见 | 用有氧记录重做 11~13 | 同饮食 | ⬜ |

> 「进入页面拉取」是本期的同步方式（无实时推送）。B 必须**重新进入页面**才看到变化。

### 4.3 离线与并发（最容易出问题的部分）

| # | 用例 | 操作 | 预期 | 状态 |
|---|---|---|---|---|
| 15 | 断网打卡 | 开飞行模式 → 新增一条饮食 | 保存成功且列表立即出现（本地优先） | ⬜ |
| 16 | 恢复网络补传 | 关飞行模式 → 重新进入打卡页 | 刚才那条**自动补传**到云端 | ⬜ |
| 17 | 补传后双端一致 | 用 B 端验证 16 的结果 | B 能看到断网期间那条记录 | ⬜ |
| 18 | 离线编辑 | 断网 → 编辑一条已上云的记录 → 恢复网络 → 重进页面 | 修改被推上去；**本地不会被云端旧值覆盖回去** | ⬜ |
| 19 | 双方同时新增 | A / B **同时**给同一天各新增一条 | 两条都保留，**不互相覆盖** | ⬜ |
| 20 | 弱网重复提交 | 网络很慢时连点两次保存 | 云端只产生一条（幂等；有唯一索引兜底） | ⬜ |

> 用例 18 是最容易出问题的一条：合并规则必须「本地有待同步修改时以本地为准」。
> 如果看到自己刚改的内容自己变回去了，说明这一步有问题，请反馈。

### 4.4 兼容与边界

| # | 用例 | 操作 | 预期 | 状态 |
|---|---|---|---|---|
| 21 | **历史数据不丢** | 用升级前打过卡的账号进入 | 此前本地保存的饮食 / 训练记录**仍然可见**（含没有 `category` 字段的老训练记录） | ⬜ |
| 22 | 老记录不被重复上传 | 检查云端 `workouts` 集合 | 不应出现历史老记录（本期不做老数据导入，留 M4） | ⬜ |
| 23 | 未登录不报错 | 退出登录后进入打卡页 | 页面正常，能本地打卡；无云错误弹窗 | ⬜ |
| 24 | 未加入家庭 | 新账号未加入家庭时打卡 | 本地可打卡；不出现云函数报错提示 | ⬜ |
| 25 | 跨家庭越权 | 用不属于该家庭的账号伪造 clientId 删除 | 云端拒绝；无法操作他人家庭数据 | ⬜ |

> 用例 21 是本期的**数据安全红线**：老训练记录没有 `category` 字段，
> 读取时按「有组明细 = 力量」推断。若老记录整批消失，说明这个推断被破坏了。

## 5. 回滚方案

| 场景 | 处理 |
|---|---|
| 前端有严重问题 | 前端回退到上一个提交即可；**云端数据不受影响**（新集合只增不改） |
| 云函数有严重问题 | HBuilderX 重新上传上一版云函数；或暂时在云函数入口 `return { code: 500 }` 熔断 |
| 需要彻底回退 | 云数据库删除 `diets` / `workouts` / `favorite_foods` 三个集合；前端回退代码 |

> 本期**没有破坏性变更**：`families` / `family_members` / `uni-id-users` 完全未改动，
> 回滚不会影响 M0/M1 已上线的登录与家庭功能。

## 6. 已知限制与遗留

| 项 | 说明 | 计划 |
|---|---|---|
| 无实时推送 | 需要重新进入页面才看到他人改动 | 后续可加轮询或 uni-push |
| 无完整离线队列 | 只有「待同步标记 + 重试上限 5 次」，无指数退避与网络状态监听 | 按路线图后续迭代 |
| 连续失败 5 次会丢弃标记 | 为防止死循环刻意如此；极端弱网下可能丢一条本地写入 | 后续可改为「保留但降频重试」 |
| 历史本地数据不上云 | 老记录只在本机可见 | M4 做「本地数据导入云端」入口 |
| 常用食物为自动收集 | 用一次的食物也会进列表 | 已按 `useCount` 排序 + 提供删除入口 |
| 支付宝云免费版到期 | **2026-10-04** | 到期前续期或升级 |
| 力量记录的热量无独立入口 | 表单已支持，但产品侧未强调 | 如需突出可再调 |
