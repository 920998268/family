## 1. 范围与验收标准

### 1.1 本期范围（M2-B）

把「学习计划打卡」从 localStorage 迁到 uniCloud，**复用 M2-A 建立的全部基建**。

| 实体 | 说明 |
|---|---|
| 学习计划 `StudyPlan` | 标题 / 学习内容 / 打卡频率 / 目标次数 / 归属成员 |
| 学习打卡 `StudyCheckin` | 计划 / 日期 / 备注 / 打卡成员 |

### 1.2 出口验收标准

1. 两个微信号 A / B 在同一家庭下，A 新增学习计划或打卡，B 重新进入页面后可见；
2. A 编辑 / 删除计划或打卡，B 重新进入后同步；
3. **A 删除学习计划后，该计划的打卡在 B 端一并消失**（级联删除生效）；
4. 断网时 A 正常打卡（本地即时生效），恢复网络后重新进入页面自动补传；
5. 两人**同时**给不同计划打卡，两条都保留；
6. **同一计划同一天不会被重复打卡**（即使两端同时点）；
7. 历史本地学习数据在本机可见、不丢失、不重复。

### 1.3 明确不做（本期）

- **老数据批量上云**——按路线图留在 M4
- 学习统计（完成率、连续天数、周报）
- `frequency`（每天 / 每周）的**服务端排期校验**——现状是「任何一天都能打卡」，
  本期保持，不做「今天不该打卡」的拦截
- 计划的归档 / 恢复（删除即删除，见 §2.2）

## 2. 需求确认结论

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 云函数拆分 | **合并为一个 `study` 云函数**（计划 + 打卡） |
| 2 | 删除计划时关联打卡 | **级联删除**，保持与现有本地行为一致 |
| 3 | 一天多条记录 | 云端**记录级 CRUD**，同一天多条互不覆盖 |
| 4 | 老数据 | 不主动上云，留 M4 |
| 5 | M2-A 验收结论 | 基本通过，当前无发现问题 |

### 2.1 为什么合并为一个 `study` 云函数

**本项目的分函数标准是业务边界，不是「一个集合一个函数」**：

| 云函数 | 操作的集合 |
|---|---|
| `family` | `families` + **`family_members`** + `uni-id-users` |
| `member` | **`families`** + `family_members` + `uni-id-users` |
| `diet` | `diets` + **`favorite_foods`** |
| `workout` | `workouts` |

已有两处「一个函数管两个集合」的先例。学习属于**主从关系**（打卡从属于计划），
存在两条跨表操作：

1. **打卡要校验计划存在**（且属于本家庭）；
2. **删计划要级联删打卡**。

第 2 条是决定性的。若拆成两个函数，级联删除只能落到：
- 让 `study_plan` 去写 `study_checkins` 集合 → 职责外泄；
- 由客户端分两步调（先删计划、再删打卡）→ **第一步成功、第二步失败会留下孤儿打卡**，
  且客户端要先把该计划散布在各个日期的打卡全查出来才能删，多一次往返且容易漏。

合并后，`removePlan` 在服务端内部完成「先删该计划全部打卡 → 再删计划」，
**一次调用、顺序由服务端保证、失败可整体重试**。

> 对外是一个函数，**对内按两块组织**：`lib.js` 分「计划」「打卡」两组纯逻辑，
> `index.js` 的 action 也分两组，职责依然清晰。

### 2.2 关于级联删除

删除计划会一并删除其全部打卡记录，这是**现有本地行为**（`StudyService.removePlan`），
本期保持一致。

这个选择是自洽的：**打卡记录本身不存计划标题，展示时必须 join 计划列表**
（`study.vue` 靠 `plans.find(p => p.id === checkin.planId)` 取标题）。
保留孤儿打卡在界面上根本渲染不出计划名，反而要做额外的兜底展示。

## 3. 数据模型设计

### 3.1 现有本地模型（`src/types/models.ts`）

```ts
interface StudyPlan {
  id: string;
  title: string;          // 必填
  subject: string;        // 学习内容，必填
  frequency: 'daily' | 'weekly';
  targetTimes: number;    // 1 ~ 1000
  memberId?: string;
  createdAt: string;      // ISO 字符串
}

interface StudyCheckin {
  id: string;
  planId: string;
  date: string;           // YYYY-MM-DD
  note: string;           // 字符串（可为空串，不可为 undefined）
  memberId?: string;
}
```

### 3.2 云端集合

| 集合 | 关键字段 |
|---|---|
| `study_plans` | familyId, clientId, title, subject, frequency, targetTimes, memberId, createdByUid, createdAt, updatedAt |
| `study_checkins` | familyId, clientId, planId, date, note, memberId, createdByUid, createdAt, updatedAt |

- `clientId` = 前端记录的 `id`（计划是 `study-xxx`，打卡是 `checkin-xxx`），幂等键；
- `familyId` **一律由服务端从 token 推导**，忽略客户端传入；
- `createdAt` / `updatedAt` 用服务端毫秒时间戳（与 `diets` / `workouts` 一致）。

> ⚠️ 注意 `StudyPlan.createdAt` 在前端是 **ISO 字符串**，而云端统一用毫秒数。
> 映射层必须做换算，不能直接透传（这正是 `cloudMap` 该管的活）。

### 3.3 索引（5 条）

| 集合 | 索引字段 | 类型 | 作用 |
|---|---|---|---|
| `study_plans` | `familyId` + `clientId` | **唯一** | 幂等写入 |
| `study_plans` | `familyId` + `createdAt` | 非唯一 | 计划列表排序 |
| `study_checkins` | `familyId` + `clientId` | **唯一** | 幂等写入 |
| `study_checkins` | `familyId` + `date` | 非唯一 | 按日拉取 |
| `study_checkins` | `familyId` + `planId` + `date` | **唯一** | **保证「同一计划同一天只打卡一次」** |

> 最后一条是本期的**实质收益**：本地只能靠应用层校验
> （`StudyService.checkin` 里的 `该计划今天已打卡`），两台设备同时点会重复；
> 唯一索引把这条规则下沉到数据库层。

## 4. 云函数设计（`study`）

### 4.1 动作路由

```
action 以 plan* 开头 → 计划相关
action 以 checkin* 开头 → 打卡相关
```

| action | 入参 | 返回 |
|---|---|---|
| `listPlans` | — | `{ code:0, data: StudyPlan[] }`（按 frequency + createdAt 降序） |
| `addPlan` | clientId, title, subject, frequency, targetTimes, memberId? | `{ code:0, data:{ _id, duplicated? } }` |
| `updatePlan` | clientId + 可改字段 | `{ code:0 }` / `404` |
| `removePlan` | clientId | `{ code:0, data:{ removed, deletedCheckins } }` |
| `listCheckins` | date | `{ code:0, data: StudyCheckin[] }` |
| `addCheckin` | clientId, planId, date, note, memberId? | `{ code:0, data:{ _id, duplicated? } }` |
| `removeCheckin` | clientId | `{ code:0, data:{ removed } }` |

### 4.2 `lib.js` 纯逻辑（可单测，自包含、不跨模块 require）

计划部分：
- `validatePlanClientId` / `validatePlanPayload`（对齐 `validateStudyPlan`）
- `mergePlanPatch(existing, patch)`
- `toClientPlan`（云端记录 → 前端模型，含 `createdAt` 毫秒 → ISO 换算）

打卡部分：
- `validateCheckinClientId` / `validateCheckinPayload`（对齐 `validateStudyCheckin`）
- `toClientCheckin`
- `buildDateWhere(dbCmd, { date })`

### 4.3 服务端要点

1. **`addCheckin` 必须先校验计划存在且属于本家庭**，否则返回 404。
   这是「打卡从属于计划」这条主从约束的落地。
2. **`addCheckin` 幂等**：按 `familyId + clientId` 查重；同时**依赖
   `familyId + planId + date` 唯一索引**兜住「两人同时打卡同一计划」。
   - 命中唯一索引冲突时，返回 `{ code:0, data:{ duplicated:true } }` 而非报错
     （离线重投不应被当成失败）。
3. **`removePlan` 级联**：先删该 `familyId + planId` 的全部打卡，再删计划。
   - ⚠️ 云函数单次 `remove()` 有条数上限，**需分批循环删除**，并在返回里带上
     `deletedCheckins` 便于排查。
   - 顺序不能反：先删计划成功、再删打卡失败 → 会留下孤儿打卡且再也找不到。
4. **`updatePlan` / `removePlan` 找不到记录返回 404**；
   **`removeCheckin` 幂等**（不存在也返回成功，避免离线队列无限重试）。
5. `memberId` 一律经 `resolveMemberId` 校验归属，非本家庭置 null。

### 4.4 复用 `common/checkin-shared`

鉴权与家庭归属推导**完全复用**，不新增公共模块。

## 6. 兼容规则

1. **老学习数据不上云**：与 M2-A 一致，本地老计划与打卡只在本机可见，留 M4 导入。
2. **`createdAt` 格式**：前端 ISO 字符串 ↔ 云端毫秒数，映射层负责换算；
   读取老记录时若遇到 ISO 字符串也要能解析（不能只认毫秒）。
3. **`note` 允许空串**：`validateStudyCheckin` 要求 `note` 是字符串（不能 undefined），
   云端返回的 `null` 要在映射层转成 `''`，否则整条打卡会被前端校验判非法而**静默丢弃**。
4. **计划被删除后的打卡**：级联删除保证不产生孤儿，前端无需兜底展示。

## 10. 风险与待确认

| # | 风险 | 处置 |
|---|---|---|
| 1 | 级联删除的**条数上限**：一个计划可能积累很多天打卡，单次 `remove()` 可能被截断 | 分批循环删除；返回 `deletedCheckins` 计数便于核对 |
| 2 | 唯一索引冲突的错误码在不同 provider 下不一致 | 捕获后**统一转成 `duplicated: true`**，不把 provider 错误码泄漏给前端 |
| 3 | `createdAt` 的 ISO ↔ 毫秒换算写错方向 | 单测固化双向换算；读取时兼容两种格式 |
| 4 | 计划是**全量拉取**，家庭计划很多时数据量大 | 本期计划数量级很小（个位数到几十），不做分页；留观察 |
| 5 | 学习打卡的「今天该不该打卡」不校验 | 产品现状，保持；若后续要加，属独立需求 |
