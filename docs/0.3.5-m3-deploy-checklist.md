## 2. 云端部署（HBuilderX，需手工操作）

### 2.1 上传 3 个 DB Schema ⬜

右键 `uniCloud-alipay` → `database` 目录 →「上传 DB Schema」（或逐个右键文件上传）：

| 文件 | 对应集合 |
|---|---|
| `meal_plans.schema.json` | `meal_plans` |
| `travels.schema.json` | `travels` |
| `travel_items.schema.json` | `travel_items` |

上传后到 uniCloud 控制台「云数据库」确认三个集合已出现。

> 三个 schema 的 `permission` **全部为 false**：客户端不能直连数据库，只能走云函数。

### 2.2 上传 `meal` 与 `travel` 两个云函数 ⬜

右键 `uniCloud-alipay/cloudfunctions/meal` →「上传部署」；
右键 `uniCloud-alipay/cloudfunctions/travel` →「上传部署」。

> **为什么是「食谱 + 出行」两个函数，而不是「膳食 + 行程明细」四个？**
> 出行计划与它的行程明细是**主从关系**（明细要校验计划存在、删计划要级联删明细），
> 所以合并在 `travel` 一个函数里；食谱与出行之间没有关联，各自独立成函数。
> 理由详见方案 §2.1。

### 2.3 ⚠️ 重传公共模块 `checkin-shared`（本期最关键的一步）

右键 `uniCloud-alipay/cloudfunctions/common/checkin-shared` →「**上传公共模块**」。

**为什么必须重传**：本期把 `TOMBSTONE_DOMAINS` 由 4 个扩到 7 个，
新增 `mealPlan` / `travelPlan` / `travelItem`。这个白名单是**双刃**的：

| 链路 | 用它的地方 | 漏改的后果 |
|---|---|---|
| **写** | `buildTombstoneDocs` 对未知 domain 直接 `return []` | 墓碑**一条都不写** |
| **读** | `listTombstones` 用 `isTombstoneDomain` 过滤 `domains` | 过滤成空 → 返回 `{ items: [] }` |

**两条链路一起失效，且零报错** —— 表现是「删除本地成功、别的设备永远看不到这次删除」，
界面一切正常、日志也没有任何异常。
（这个缺陷在第 4~6 步之间真实存在过，是第 6 步排查时发现的。）

> 重传后 `diet` / `workout` / `study` 三个老云函数**不需要**重新部署 ——
> 它们引用的是同一个公共模块，内容更新后自动生效。

### 2.4 ⚠️ 重传 `study` 云函数

右键 `uniCloud-alipay/cloudfunctions/study` →「上传部署」。

**为什么必须重传**：本期统一了 `removePlan` 的墓碑口径
（见 `0.3.4-cross-device-delete-sync.md` §3.2 与提交 `2cd2e6d`）——
原先「计划记录不存在就早返回」，违反了「墓碑无条件写」这条铁律。

不重传**不会出错**（维持旧行为），但会少一次「重试补写墓碑」的机会：
「计划已删、写墓碑失败」时客户端会重试，重试时 `findPlan` 已经查不到记录了 ——
旧版本会在这里直接返回，这条墓碑就**永远补不上**。

### 2.5 更新 `checkin_tombstones` schema（可选）

右键 `uniCloud-alipay/database/checkin_tombstones.schema.json` →「上传 DB Schema」。

本期只改了 `domain` 字段的**说明文字**（枚举由 4 个写到 7 个），
`maxLength` 未变、`required` 未变 —— 属**文档性更新**，不传也不影响功能。
传了的好处是以后在控制台看字段说明时不会误以为只有 4 个 domain。

### 2.6 建 6 条索引 ⬜

> 项目里没有 `db_init.json`，uniCloud 的 db-schema 也**不支持声明索引**，
> 所以索引只能在控制台手工建（与云函数、schema 一样属于「必须手工做」的部分）。

#### 入口

uniCloud web 控制台 →「**云数据库**」→ 左侧选中集合 →「**索引管理**」标签 →「**新建索引**」。

> 最省事的打开方式：在 HBuilderX 里右键 `uniCloud-alipay` 目录 →
> 「**打开 uniCloud web 控制台**」，会自动带上当前服务空间。

#### 逐条填写参数

| 集合 | 索引名（建议） | 字段与排序 | 唯一 | 用途 |
|---|---|---|---|---|
| `meal_plans` | `idx_family_client` | `familyId` 升序, `clientId` 升序 | ✅ **是** | 幂等键 |
| `meal_plans` | `idx_family_date` | `familyId` 升序, `date` 升序 | 否 | 按日期拉取（最高频路径） |
| `travels` | `idx_family_client` | `familyId` 升序, `clientId` 升序 | ✅ **是** | 幂等键 |
| `travels` | `idx_family_start` | `familyId` 升序, `startDate` **降序** | 否 | 列表排序（与本地 `list()` 的降序一致） |
| `travel_items` | `idx_family_client` | `familyId` 升序, `clientId` 升序 | ✅ **是** | 幂等键 |
| `travel_items` | `idx_family_travel` | `familyId` 升序, `travelId` 升序, `order` 升序 | 否 | 取某计划的明细 + 级联删除定位 |

> **`travel_items` 刻意不加 `familyId + travelId + order` 唯一索引**：用户完全可能
> 把两行都留空、或写同样的时间，顺序冲突用排序稳定化处理即可；
> 加唯一索引只会让**正常编辑**报错。

#### 三个容易出错的点

1. **复合索引的字段顺序不能颠倒**：所有查询都带 `familyId`，所以它**必须放第一位**。
   顺序错了索引就用不上（查询退化成全表扫描），而且**不会报错**，很难发现。
2. **建唯一索引前，表里不能已有重复值**。三个集合都是本期新建的空集合，正常不会有问题；
   但如果你手动插过测试数据，请先删掉重复项再建，否则创建会失败（报重复键）。
3. **索引建好立即生效，不需要重新上传云函数**；反过来，删掉唯一索引也不会报错，
   但会**悄悄失去幂等保护** —— 别为了「让写入先跑通」去删它。

#### 怎么确认建对了

「索引管理」列表里应当能看到 6 条，且 3 条带「唯一」标记。
建完后可以顺手在「数据查询」里手动插入一条重复的 `familyId + clientId` 记录，
**预期被拒绝** —— 能拒绝就说明唯一索引真的生效了。

### 2.7 部署后自检 ⬜

**方式 A（推荐，零控制台依赖）**：打开 H5（`npm run dev:h5`）→ F12 → Console：

```js
// 食谱
uniCloud.callFunction({ name: 'meal', data: { action: 'list', date: '2026-09-12' } })
  .then(r => console.log('meal.list      ', r.result))
// 出行计划
uniCloud.callFunction({ name: 'travel', data: { action: 'listPlans' } })
  .then(r => console.log('travel.listPlans', r.result))
// ⚠️ 墓碑通路（验证 §2.3 的 checkin-shared 是否真的生效）
uniCloud.callFunction({ name: 'meal', data: { action: 'listTombstones', since: 0 } })
  .then(r => console.log('meal.listTombstones', r.result))
```

对照结果：

| 返回 | 含义 | 处理 |
|---|---|---|
| `{"code":0,"data":[...]}` / `{"code":0,"data":[]}` | ✅ **全链路正常** | 进入 §3 |
| `{"code":401,"msg":"登录态无效或已过期"}` | ✅ 云函数与公共模块都正常，只是无登录态 | 先登录再试 |
| `{"code":400,"msg":"尚未加入家庭"}` | ✅ 鉴权通过，账号未加入家庭 | 正常 |
| `Cannot find module 'checkin-shared'` | ❌ 公共模块缺失 | 回到 §2.3 重传 |
| 集合不存在 / `collection not exists` | ❌ schema 没传成功 | 回到 §2.1 重传 |
| `未知操作: xxx` | ⚠️ 云函数是旧版本 | 回到 §2.2 重传 |
| **`listTombstones` 返回 `{"code":0,"data":{"items":[]}}`** | ✅ 也可能只是当前没有墓碑 | 见下方「墓碑通路专项验证」 |

#### 墓碑通路专项验证（本期新增，务必做一次）

上面那个空数组**不能**区分「没有墓碑」和「白名单没生效」——两者长得一模一样。
用一个**会产生墓碑的动作**来验：

1. 在前端新建一条食谱记录，等它同步成功（换设备/重进页面能看到）；
2. 把它删掉；
3. 到控制台「云数据库」→ `checkin_tombstones` 集合查看，**应当出现一条**
   `domain: 'mealPlan'` 的记录；
4. 再用 `listTombstones` 拉一次，应当能拿到它。

> 若第 3 步查不到记录 → `checkin-shared` 没传成功或传的是旧版，回到 §2.3。
> 这一步同时验证了「写」和「读」两条链路，**不要跳过**。

## 5. 故障排查

M2-A 清单 §7 的三节仍然适用，本期补充：

| 现象 | 排查 |
|---|---|
| 食谱 / 出行数据不上云，但界面一切正常 | 按 M2-A 清单 §7.3 的两步法：先看 Local Storage 有没有 `uni_id_token`，再看 `family.pendingSync.v1` 的 `attempts` 与 `lastError`。**本期新增了 3 个 domain**：`mealPlan` / `travelPlan` / `travelItem`，标记里的 `domain` 可用来判断是哪一类 |
| **删除本地成功、别的设备永远看不到删除** | ⚠️ 十有八九是 `checkin-shared` 没重传（见 §2.3）。到控制台看 `checkin_tombstones` 有没有记录 —— 没有就是白名单没生效 |
| `Cannot find module 'checkin-shared'` | 公共模块没传成功，重传 §2.3 |
| `未知操作: xxx` | 云函数是旧版本，重新上传部署 |
| `travel_items` 里出现找不到计划的孤儿明细 | 只可能来自手工插入；`addItem` 会强制校验计划存在，正常路径不会产生 |
| 删除计划时报「该计划的行程明细较多，本次未清理完」 | **设计行为**：服务端不会带着未删完的明细删计划（否则留下孤儿）。**重试即可**，每轮都有进展 |
| 勾选后两端状态不一致 | 检查是否用了旧版前端（在线勾选应直连服务端翻转、并用返回值校正本地）；离线勾选会在恢复网络后由队列补推 |
| 明细顺序两端不一致 | 检查 `travel_items` 的 `order` 字段是否有值；老数据缺 `order` 时靠 `fallbackOrder`（数组下标）兜底 |
