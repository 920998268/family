## 版本概述

0.3.4 是**跨设备删除同步**整改版本（对应 `docs/0.3.4-cross-device-delete-sync.md`）。

**修的是什么**：A 删掉一条饮食 / 运动 / 学习记录后，B 重新进入页面**仍然看得到它**。

**为什么会这样**：两条既有设计叠加的结果 ——

1. 云端 `remove` 是**物理删除**，记录从云端消失、不留任何痕迹；
2. 合并规则刻意保留「本地有、云端没有」的记录。

第 2 条本身是**必需的**（它保护弱网下「本地刚新建、还没推上云」的数据），
但配上第 1 条之后，B 端**无法区分**「云端已被别的设备删除」和「从未上云」——
两者都表现为「云端列表里没有这条 id」，于是 B 一律保留。

**怎么改的**：引入**删除日志（墓碑）**集合，把删除变成**显式事件**，
其他设备按日志删除本地记录。这也是**唯一安全**的做法 ——
更简单的「云端没有即删除」（全量覆盖）会误删用户设备上大量
M2 之前从未上云的历史数据（老数据导入明确留到 M4），见方案文档 §2.1。

## 一、整改内容

### 1. 新增删除日志集合 `checkin_tombstones`

| 字段 | 类型 | 说明 |
|---|---|---|
| `familyId` | string | 家庭 id（服务端推导，不接受客户端传入） |
| `domain` | string | `diet` / `workout` / `studyPlan` / `studyCheckin` |
| `clientId` | string | 被删记录的幂等键（= 前端记录 id） |
| `date` | string | 被删记录的日期，学习计划为空串（用于客户端快速定位） |
| `deletedAt` | number | 删除时间（毫秒），**游标依据** |
| `createdByUid` | string | 删除操作人 |

索引 `idx_family_deleted`（`familyId` + `deletedAt`）用于按家庭 + 游标增量拉取。

> **故意不加** `familyId + clientId` 唯一索引：同一条记录可能被删多次
> （删除 → 重新添加 → 再删除），按 `deletedAt` 增量消费即可，无需去重。

### 2. 三个云函数的删除改为「删除 + 写墓碑」

```
① 查记录（familyId + clientId）
② 若存在 → 物理删除
③ 写墓碑（无论记录是否存在都执行）
④ 返回 { removed: ②是否发生 }
```

第 ③ 步**无论记录是否存在都要写**：这样「删除成功但墓碑写入失败」时，
客户端重试能补上墓碑（重试时 ② 返回 `removed: false`，③ 照常写）。

> 顺序不能反。「先写墓碑后删记录」一旦删除失败，其他设备已经删掉了本地记录，
> 而 A 下次拉取时云端记录还在 → **记录复活**，比残留严重得多。

`study.removePlan` 级联删除时会**为每一个被删打卡补一条墓碑**，
否则 B 端会出现「计划没了但打卡还在」的孤儿打卡。
（删打卡本身沿用 M2-B 的分批循环：**未删完时不删计划、不写墓碑**，返回可重试错误。）

### 3. 客户端增量消费：游标 + 删除优先

- 本地存储键 `family.tombstoneCursor.v1` 记录已应用到的最大 `deletedAt`；
- 四个拉取入口（`pullDiets` / `pullWorkouts` / `pullStudyPlans` / `pullStudyCheckins`）
  **在读本地之前**先应用墓碑 —— 顺序错了会先读到已删除的记录并把它合并回本地；
- **删除优先**：若被删记录在本机还有待同步标记，一并丢弃。
  否则推送的 `add` 分支会把记录**重新创建**到云端 → A 端又看到它 → 两端来回横跳；
- 单次拉取上限 500 条，只取最近 **180 天**的墓碑（覆盖「设备半年不联网」的极端情况）；
- 墓碑拉取失败**只告警不抛出**，不阻塞正常的云端数据拉取。

> **store 层零改动**：三个 store 的 `syncFromCloud` 本来就调用上述拉取方法，
> 墓碑应用放进方法内部即自动对三个打卡页面生效。

### 4. 不误删的三重保证

1. **只依据显式墓碑事件删除** —— 本地「从未上云、也没有待同步标记」的历史记录
   不可能出现在墓碑里，天然安全；
2. **解析时丢弃非法项** —— `clientId` 为空的墓碑条目直接跳过，
   宁可漏删也不能误删；
3. **定位不到就全量兜底** —— 按 `date` 定位失败时扫描全部日期分区，
   避免脏数据导致「怎么都删不掉」。

## 二、Bug 修复

### 1. 「存储键日期 ≠ 记录 date」的脏数据删不掉

按墓碑删除本地记录时，第一版只用**记录自身的 `date` 字段**定位存储分区。
但历史脏数据可能存在「存放在 A 日期的键下、`date` 字段却是 B」的情况 →
表现为「这条记录怎么都删不掉」。

已改为**同时清两个日期**（记录自身的 `date` + 墓碑携带的 `date` 兜底）。
**这条是双机端到端测试逼出来的**，不是靠读代码发现的。

## 三、优化改进

1. **云函数公共模块拆出纯逻辑**：`checkin-shared/lib.js` 承接墓碑的构造 / 校验 /
   游标 / 转换逻辑（可单测），`index.js` 只保留数据库动作 —— 沿用该模块既有的分层约定；
2. **新增 74 项墓碑用例**：`tombstone-shared`（16）/ `tombstone-cloud`（19）/
   `tombstone-utils`（19）/ `tombstone-sync`（20）。
   其中 `tombstone-sync` 含 **4 项双机端到端**用例（内存假云端 + 两台设备），
   直接验证「A 删除 → B 拉取时消失」；
   另有 8 项文档/版本守卫（版本说明体例、`checkin-shared` 必须重传、
   **版本号三处一致**）—— 本版合计 541 → **632 项**；
3. **顺序守卫**：把四条顺序铁律固化为断言 ——
   先删记录后写墓碑 / 级联删除先收集打卡再删 / 未删完不写墓碑 / 打卡墓碑先于计划墓碑；
4. **部署经验固化**：本期 `checkin-shared` **必须重传**（M2-B 那期恰好相反），
   两期结论相反最易照旧习惯漏掉，已用文档守卫显式锁住。

## 四、已知限制

1. ✅ **云端部署与 10 条真机用例已于 2026-09-13 全部通过**。
   步骤见 `docs/0.3.4-cross-device-delete-sync-checklist.md`。
2. **历史已删除的数据不补**：墓碑从部署生效之日起才开始写，
   在此之前被删除的记录在别的设备上的残留**不会被追溯清理**，
   在残留设备上手动删一次即可（那些记录本来就在用户自己的设备上）。
3. **墓碑不自动清理**：超过 180 天的墓碑不再返回但也不会被删除。
   家庭场景量级可忽略；将来需要可加惰性清理或定时云函数。
4. **未改「重试超限丢弃标记」策略**：该策略仍有改进价值
   （标记被丢弃后记录永远上不了云），但它是独立课题，不阻塞本次整改。
5. **老数据不主动上云**：0.3.2 之前的本地打卡记录仍只在本机可见，批量导入留到 M4。
6. **无实时推送**：他人改动需要重新进入页面才能看到（仍为「进入页面拉取」）。
7. 学习以外的食谱 / 出行 / 账本仍为 localStorage 实现（M3 / M4）。
8. 支付宝云免费版 **2026-10-04 到期**，需关注续期。

### 1. 云侧部署（**必须在 HBuilderX 手工完成**，共 6 项）

支付宝云不支持 CLI 发行，以下操作无法通过命令行完成。
**逐项清单见 `docs/0.3.4-cross-device-delete-sync-checklist.md`**，摘要：

| # | 上传项 | 说明 |
|---|---|---|
| 1 | DB Schema `checkin_tombstones` | 新增集合 |
| 2 | 索引 `idx_family_deleted` | `familyId` + `deletedAt`，**非唯一** |
| 3 | 公共模块 `common/checkin-shared` | ⚠️ **本期必须重传**（新增 `lib.js` 与两个导出） |
| 4 | 云函数 `diet` | 删除写墓碑 + `listTombstones` 路由 |
| 5 | 云函数 `workout` | 同上 |
| 6 | 云函数 `study` | 同上 + 删计划的级联墓碑 |

**先 1 → 2 → 3，再 4 / 5 / 6。**（公共模块必须在云函数之前，云函数运行时会 `require` 它。）

> ⛔ **不要用「上传所有云函数、公共模块及 actions」**：
> 该操作会连带重传 `uni-config-center`，而 HBuilderX 的公共模块来源目录里
> 并没有 `uni-id/config.json`，重传会导致**所有登录/注册接口报
> `Invalid uni-id config file`**（M2-A 时实际踩过）。
