# 家庭打卡小程序 0.4.0 版本说明

**版本号：** v0.4.0
**发布日期：** 2026-09-14
**上一版本：** v0.3.5

---

## 版本概述

0.4.0 是**账本上云 + 老数据一次性搬上云**版本
（对应 `docs/0.4.0-m4-requirements-and-solution.md`，M4）。

**做了什么**：两件事，且**必须同一版交付**。

1. 把「家庭收支账本」从**纯本地存储**接入云端（支付宝云），实现双端可见、
   离线可用、跨设备删除同步 —— 这是六个业务模块里**最后一个**仍只存在于本机的模块；
2. 新增「**本地数据导入云端**」入口：把此前几个月躺在手机里、
   从未上过云的历史数据（饮食 / 运动 / 学习计划 / 学习打卡 / 食谱 / 出行计划 /
   出行明细 / 收支）一次性认领到云端。

**为什么必须同一版**：账本一旦上云，「老数据上不去云」的影响面就从
「某一类模块」扩到「所有模块」—— 用户会把「我的历史记录怎么只有这台手机有」
归因于整个上云能力。所以验收口径是**导入入口与账本上云同时可用**，不拆版发布。

**本期与 M2 / M3 最本质的差别**：M2 / M3 解决的是「**新**数据怎么上云」，
本期要解决「**已经躺在手机里几个月的数据怎么一次性搬上去**」。
这是项目里**第一个跨全部 domain 的功能**。

| 指标 | v0.3.5 | v0.4.0 |
|---|---|---|
| 单元测试 | 928 项 / 44 文件 | **1148 项 / 52 文件** |
| 云端集合 | 12 | **13**（+ `transactions`） |
| 云函数 | 8 | **9**（+ `ledger`） |
| 索引 | 17 | **19**（+ 2） |
| 墓碑 domain | 7 | **8**（+ `transaction`） |
| type-check | 通过 | 通过 |

> 本期**数据零迁移**：`diets` / `workouts` / `study_*` / `favorite_foods` /
> `meal_plans` / `travels` / `travel_items` / `families` / `family_members` /
> `uni-id-users` 的既有字段与数据一行未动；
> `checkin_tombstones` 只改了 `domain` 字段的**说明文字**（无功能影响）。
> 回滚不会损坏既有数据。

## 一、新增能力

### 1. 账本上云：新云函数 `ledger` + 新集合 `transactions`

| 云函数 | 集合 | 说明 |
|---|---|---|
| `ledger` | `transactions` | 收支记录，**按日期**组织（同 `diets` 的形态） |

沿用 M2 已成熟的形态：**记录级 CRUD + `familyId` 服务端推导 + `clientId` 幂等键 +
删除写墓碑**。action 集合（5 个）与 `meal` 完全同构。

> 账本**单独一个云函数**，判据仍是 M2 确立的「**存在主从关系才合并**」——
> 账本没有子实体、不涉及级联删除，没有并入其它函数或拆成多个的理由。

### 2. 拉取通路是「日期区间」—— 与 M2 的单日、M3 的全量都不同

账本页的汇总卡（收入 / 支出 / 结余）是对**当前选中月份**的全部记录求和，
所以拉取必须覆盖整月：

| 期 | 通路口径 |
|---|---|
| M2 | 按**单日**（diet / meal / studyCheckin） |
| M3 | **全量** + 按所属计划（travel） |
| **M4** | **日期区间** `pullTransactions(from, to)` |

> ⚠️ 只拉当天会让月汇总基于残缺数据算出**明显偏小的数字** ——
> 用户立刻会察觉「我的账是不是记错了」。回写也必须**按 `date` 分桶逐桶写**
> （整段覆盖会把某一天的记录抹掉）。

### 3. ★ 本地数据导入云端（本期最大的改动，也是最早的承诺）

这条能力从 M2-A 起就明确「老数据不主动上云，批量导入留到 M4」，
在四处文档里都写着。本期兑现。

> ⚠️ **「导入」有两个方向，最容易混淆**：
>
> | 方向 | 现有能力 | 本期 |
> |---|---|---|
> | 云 → 本机 | `BackupService.import`（备份 JSON 文本 → 本机，**会先清空本机再写入**） | 不做 |
> | **本机 → 云** | **此前不存在** | ✅ **本期新建** |
>
> 两者不复用 UI，也不共用序列化逻辑：前者搬的是「备份文件」，后者做的是「**数据认领**」。
> 本期新增的是**上行**这一半。

```
① 前置检查：已登录 + 已加入家庭（未满足则直接提示，不产生任何标记）
② 本机读全量：复用 BackupService.export() —— 它已经能拿到全部 8 个 domain
③ 归一：补齐 / 校正云端必需形态、按依赖顺序排列（计划先于打卡 / 明细）、
        被改动过的字段记进 fixes（用于报数，不静默改数据）
④ 限并发 6 逐条上行，逐条独立成败
⑤ 汇总报数：成功 / 已在云端（幂等跳过）/ 失败 + fixes 明细，本机留档供页面展示
⑥ 此后新增 / 编辑走正常的「本地优先 + 待同步标记」通路，与导入无关
```

**五条必须成立的性质**（验收依据）：

| 性质 | 含义 |
|---|---|
| **幂等** | 云端按 `clientId` 去重，命中计入「已在云端」。导入**可以重复点、可以失败后重跑** |
| **逐条独立** | 一条脏数据只让**这一条**失败并被回报（含原因与 `clientId`），不影响其余 |
| **不排待同步标记** | 导入是「直连写」，全程不落 `pendingSync` —— 否则一次导入会凭空造出几千条标记 |
| **报数不静默** | 统计以「本机实际能读出的条数」为基准，`fixes` / `invalid` 摊开给用户看 |
| **可重入** | 每完成一条就更新进度；某一条失败重跑即可补齐 |

> 💡 **导入没有自己的云端代码** —— 原方案打算给账本加一个批量 action
> `importAll`，实施时发现导入要跨 **8 个 domain、6 个云函数**：只给 `ledger` 加
> 解决不了其余 7 个，给 6 个都加则要**重传 5 个已部署的云函数**。
> 改为**复用各域既有的 `create()`** 后，导入与正常写入走**完全同一条服务端代码路径**，
> 不可能出现「导入能写、正常写不能写」的契约漂移 —— 这也让本期**不需要重传任何既有云函数**。

### 4. 跨设备删除同步扩展到第 8 个 domain

0.3.4 建立的**墓碑（删除日志）**机制，本期把白名单由 7 个 domain 扩到 8 个：
新增 `transaction`。

> ⚠️ 这里有一个**必须重传公共模块**的部署要点，见 §五.1 与部署清单 §2.3。
> 漏传的后果是「删除本地成功、别的设备永远看不到」且**全程零报错**。

## 二、Bug 修复

本期修掉 4 个既有缺陷，其中 3 个是**上云之后才会暴露**（或只在构建时暴露）的那一类。

### 1. ⚠️ 编辑态改日期必然失败（纯本地时代就存在）

`record.vue` 的 `save()` 用 `date.value` 定位记录，而 `date.value` 会被日期选择器改写。
于是「打开一条旧记录 → 改日期 → 保存」会命中：
`getByDate(新日期)` 里**找不到这条记录** → 抛「未找到要编辑的收支记录」→ 界面弹「保存失败」。
删除同理 —— 改过日期之后连删除也会失败。

上云之后这个缺陷**更危险**：`date` 一旦与本机分区不一致，
记录会在**按区间拉取**时凭空消失。

**已修**：编辑态把日期选择器**置为只读**（新增态仍可改）。
理由是 `date` 既是本机分区键、又是云端拉取维度，允许改就要引入「跨分区移动」语义
（删旧 + 建新 + 写墓碑），复杂度不成比例；而用户的实际诉求是「这条记错日期了」，
删掉重记一次即可。

### 2. ⚠️ 账本备注没有长度上限

`validateTransaction` 对 `note` 只要求「是字符串」，表单也没有 `:maxlength`。
上限一旦只存在于云端，就会复现 M2 / M3 反复踩过的那个坑：
用户能输入超长内容 → 本地写入成功（界面一切正常）→ 推云端 400 →
重试 5 次后**丢弃待同步标记** → 记录永久留在本机、云端没有，**全程不报错**。

**已修**：新增 `LEDGER_LIMITS = { note: 100, category: 20 }`，三处对齐
（表单 `:maxlength` ↔ 云侧 `lib.js` 常量 ↔ Schema 的 `maxLength`），
并接入既有的三角闭合守卫。

> ⚠️ **刻意不给 `validateTransaction` 加长度校验**：本机仓储是「校验不通过即丢弃」，
> 加上限会让**历史里备注超长的整条记录被判非法后静默消失**
> —— 这正是 M3 在 `order` 字段上踩过的同款坑。上限只存在于**表单**与**云端**两端。

### 3. 账本页「本月结余」卡与「收入 / 支出」卡在部分机型贴在一起

账本页的三个统计卡共用 `.section` 块级容器，而该容器**没有设置任何间距** ——
卡片之间的垂直间隔实际为 0，视觉上完全依赖卡片自身的内边距撑着。
余额位数变多、或系统字体放大时，两张卡就会看起来**粘在一起甚至重叠**，
在部分机型（字体缩放不同）上尤其明显。

**已修**：给 `.stat-card` 显式加 `margin-bottom`。

> 刻意用 **`margin` 而不是 flex 的 `gap`**：`gap` 在旧 WebView
> （iOS < 14.1 / Android WebView < 84）上无效，用 `gap` 会在这些机型上
> **原样复现**「部分机型贴在一起」的现象 —— 而小程序基础库在旧设备上正是这种情况。
> 这条已写进源码注释与回归守卫（`tests/ledger-store.test.ts`）。

### 4. ⚠️ `build:mp-weixin` 因未定义的 SCSS 变量一直失败

`src/pages/backup/backup.vue` 里写了 `background-color: $uni-bg-color-grey`，
而本项目的 `src/uni.scss` **没有定义这个变量** →
构建直接报 `Undefined variable`。

危险之处在于**它能带病一路走到发版前**：

| 检查 | 是否编译 SCSS | 结果 |
|---|---|---|
| `npm test` | ❌ 不编译 | ✅ 全绿 |
| `npm run type-check` | ❌ 不编译 | ✅ 0 错误 |
| `npm run build:mp-weixin` | ✅ 编译 | ❌ 失败 |

**已修**：改用已定义的 `$uni-border-color`；并新增 `tests/scss-vars.test.ts`
把「所有 `$uni-*` 变量都必须在 `uni.scss` 里定义」固化成断言
（脚本里塞一个假变量会被精确报出文件与变量名）。

> 教训：**`npm test` + `type-check` 全绿不等于能发版**。
> 发版前的构建这一步不能省，已写进部署清单 §1。

## 三、优化改进

1. **全 domain 接通守卫扩到 8 个**：给 8 个 domain 各放一条本地记录 + 各排一条待同步标记，
   `flush()` 后要求全部成功、零丢弃 —— 专抓「漏接一条推送分支」这类静默失败
   （同步层的 `default: skip` 分支会把未知 domain 当成「本地无内容可推」直接放弃）；
2. **长度上限的三角闭合守卫扩到账本**：前端 `limits.ts` ↔ 云侧 `lib.js` ↔ Schema 的
   `maxLength` 三处一致，并额外留一处**绝对值基准** + 方向性断言「schema 不得比 lib 更严」；
3. **新增 SCSS 变量守卫**：见 §二.4 —— 补上「两个不编译 SCSS 的检查都通过、
   但构建失败」这个盲区；
4. **账本 store 的「按响应月份回读」**：切月份时会发起云端拉取，
   响应回来时必须按**这次请求对应的月份**回读（`readMonth(month)`），
   而不是「当前月份」（`read()`）—— 否则用户快速来回切月份时，
   先发出的那次响应会把后一次的数据覆盖掉。
   ⚠️ 这条守卫的第一版是**假的**：实现写成 `read()` 时守卫成了恒真式，
   整块删掉都没有用例失败。改成参数化回读后，删掉守卫立刻有用例红。
5. **每一处新守卫都做了变异验证**：故意改坏实现，确认对应用例会红。
   本期累计验证 47 组变异（第 4 步 9 组 / 第 5 步 6 组 / 第 6 步 12 组 /
   第 7 步 26 组，含跨步复核）。

## 四、已知限制

1. ✅ **云端部署（5 项）与 43 条真机用例已于 2026-09-14 全部通过**。
   步骤与结果见 `docs/0.4.0-m4-deploy-checklist.md` §7。
   其中「墓碑通路专项验证」也已通过 —— 注意单看 `listTombstones` 返回空数组
   无法区分「没有墓碑」和「白名单没生效」，必须走一次
   「记一笔 → 删除 → 查 `checkin_tombstones` → 换设备确认消失」。
   同一次自检里还**回归验证了老模块（饮食打卡）的删除传播**，
   确认白名单改动是「8 个值的完整集合」、没有写漏。
2. **账本展示顺序不是时间序**：`LedgerService` 用 `id` 排序，
   而 `createId` 在支持 `crypto.randomUUID` 的环境（H5）会产出**随机 UUID** ——
   同一天内的先后顺序在 H5 上看起来是随机的（小程序端降级为时间前缀，看起来正常）。
   本期刻意不改（改它会动到所有账本记录的展示顺序，属体验变更），仅记录在案。
3. **金额是浮点数**：`0.1 + 0.2` 类误差沿用现状（前端本来就是 `number` 累加），
   本期不做定点数。
4. **`list` 单次上限 500 条**：按月区间正常不会触顶（要连续 31 天每天记 16 笔以上）；
   真触顶时会**报「拉取被截断」**，不静默少数据。
5. **不做「按 domain 选择性导入」**：一次全导，简单且幂等。
6. **导入不做断点续传协议**：靠**幂等**支持「失败后整批重跑」。
7. **历史超长备注不在导入时截断**：上限只在表单与云端，导入不做静默裁剪 ——
   若真出现超长历史数据，走 `invalid` 明确报出来，而不是悄悄改用户的数据。
8. **无实时推送**：他人改动需要重新进入页面才能看到（仍为「进入页面拉取」）。
9. **墓碑不自动清理**：超过 180 天的墓碑不再返回但也不会被删除（同 0.3.4）。
10. **重试超限仍会丢弃标记**：标记连续失败 5 次后放弃，该记录停留在本地。
    这是 0.3.4 就遗留的独立课题。
11. 支付宝云免费版 **2026-10-04 到期**，需关注续期。
    由此推出一条设计约束：本期**没有使用任何支付宝云特有的 API / 方言 / 专用扩展**，
    云函数与 schema 只用通用的 `where / orderBy / limit / add / doc().update|remove` 与
    `bsonType / required / permission / maxLength`，将来迁移只需改服务空间配置并重新上传。

## 五、升级与发布说明

### 1. 云侧部署（**必须在 HBuilderX 手工完成**，共 5 项）

支付宝云不支持 CLI 发行，以下操作无法通过命令行完成。
**逐项清单见 `docs/0.4.0-m4-deploy-checklist.md`**，摘要：

| # | 上传项 | 说明 |
|---|---|---|
| 1 | DB Schema `transactions` | 新集合 |
| 2 | 云函数 `ledger` | 账本（单表，5 个 action） |
| 3 | 公共模块 `common/checkin-shared` | ⚠️ **本期必须重传**（`TOMBSTONE_DOMAINS` 7 → 8） |
| 4 | DB Schema `checkin_tombstones` | 仅字段说明文字更新（文档性，可选） |
| 5 | 2 条索引 | 见部署清单 §2.5 |

**先 3（公共模块），再 1 / 2。** 公共模块必须在云函数之前 —— 云函数运行时会 `require` 它。

> ✅ **与 M3 的差别**：本期**没有既有云函数需要重传**。
> M3 因统一 `removePlan` 的墓碑口径必须重传 `study`；本期账本的全部代码
> 都只写在**新增的 `ledger`** 里，`diet` / `workout` / `study` / `meal` / `travel`
> 五个云函数保持原样。

> ⛔ **不要用「上传所有云函数、公共模块及 actions」**：
> 该操作会连带重传 `uni-config-center`，而 HBuilderX 的公共模块来源目录里
> 并没有 `uni-id/config.json`，重传会导致**所有登录/注册接口报
> `Invalid uni-id config file`**（M2-A 时实际踩过）。

> ⚠️ **重传 `checkin-shared` 时务必确认白名单是 8 个值的完整集合**，
> 不是只剩 `transaction` —— 白名单是**替换**语义，写漏会把老模块
> （饮食 / 运动 / 学习 / 食谱 / 出行）的删除传播**一起**弄坏。
> 部署清单 §2.6 里专门加了一步「删一条饮食打卡」的回归验证。

### 2. 前端构建

```
npm run build:mp-weixin     # 产物 dist/build/mp-weixin → 微信开发者工具打开
npm run build:h5            # 产物 dist/build/h5
```

> 本期**前端代码与云侧代码两边都改了**，所以**两边都要做**。
> 判断口诀始终是：**改哪边传哪边**。
>
> ⚠️ **构建这一步本期不是走过场**：`npm test` 与 `type-check` 都**不编译 SCSS**，
> 二者全绿时构建仍可能失败（见 §二.4）。发版前一定要真的跑一次。

> 微信公众平台合法域名本期**无需改动**，具体值见 `docs/0.3.2-m2a-deploy-checklist.md`。

### 3. 部署后自检（不用真机，1 分钟）

H5 页面 Console 中执行（**两条都要看**）：

```js
uniCloud.callFunction({ name: 'ledger', data: { action: 'list', from: '2026-09-01', to: '2026-09-30' } }).then(r => console.log(r.result))
uniCloud.callFunction({ name: 'ledger', data: { action: 'listTombstones', since: 0 } }).then(r => console.log(r.result))
```

| 返回 | 含义 |
|---|---|
| `{code: 0, data: [...]}` | ✅ 全链路正常 |
| `未知操作: xxx` | ❌ 云函数还是旧版本，重新上传 |
| `Cannot find module 'checkin-shared'` | ❌ 公共模块没传成功 |
| 报集合不存在 | ❌ schema 没传 |

> ⚠️ **`listTombstones` 返回空数组不能说明问题** —— 「没有墓碑」和
> 「白名单没生效」长得一模一样。必须按部署清单 §2.6 的「墓碑通路专项验证」
> 走一遍：**记一笔账 → 删除 → 到控制台看 `checkin_tombstones` 里有没有
> `transaction` 记录 → 换设备确认它消失了**。
