## 2. 云端部署（HBuilderX，需手工操作）

### 2.1 上传 `transactions` DB Schema ⬜

右键 `uniCloud-alipay/database/transactions.schema.json` →「上传 DB Schema」。

上传后到 uniCloud 控制台「云数据库」确认 `transactions` 集合已出现。

> schema 的 `permission` **全部为 false**：客户端不能直连数据库，只能走云函数。
>
> 三个 `maxLength` 与前端 `LEDGER_LIMITS` 逐项一致（`clientId` 64 / `category` 20 /
> `note` 100），有 `tests/ledger-schema.test.ts` 与 `tests/ui-limits.test.ts`
> 做三角闭合守卫 —— **不要为了「让写入先跑通」去放宽它**。

### 2.2 上传 `ledger` 云函数 ⬜

右键 `uniCloud-alipay/cloudfunctions/ledger` →「上传部署」。

> **为什么账本单独一个云函数，而不是并进别的？**
> 沿用 M2 确立的判据「**存在主从关系才合并**」：账本没有子实体、不涉及级联删除，
> 与 `meal` 同构，没有并入其它函数或拆成多个的理由。理由详见方案 §2.1。

本期 `ledger` 的 action 集合（5 个，与 `meal` 完全同构）：

| action | 说明 |
|---|---|
| `list` | 入参 `{ from, to }`（闭区间，`YYYY-MM-DD`），返回该区间内本家庭的收支记录 |
| `add` / `update` / `remove` | 记录级 CRUD；`remove` **先删记录、后写墓碑**（墓碑**无条件写**） |
| `listTombstones` | 墓碑增量拉取（`domain: 'transaction'`） |

> ⚠️ 账本**没有** `importAll` 这类批量接口 —— 老数据导入复用各域既有的 `create()`
> 逐条下发（方案 §2.1 决策 3）。所以本期账本**不需要任何自己独有的写入规则**。

### 2.3 ⚠️ 重传公共模块 `checkin-shared`（本期最关键的一步）

右键 `uniCloud-alipay/cloudfunctions/common/checkin-shared` →「**上传公共模块**」。

**为什么必须重传**：本期把 `TOMBSTONE_DOMAINS` 由 7 个扩到 8 个，新增 `transaction`。
这个白名单是**双刃**的：

| 链路 | 用它的地方 | 漏改的后果 |
|---|---|---|
| **写** | `buildTombstoneDocs` 对未知 domain 直接 `return []` | 墓碑**一条都不写** |
| **读** | `listTombstones` 用 `isTombstoneDomain` 过滤 `domains` | 过滤成空 → 返回 `{ items: [] }` |

**两条链路一起失效，且零报错** —— 表现是「删除本地成功、别的设备永远看不到这次删除」，
界面一切正常、日志也没有任何异常。

> 这不是假想的风险：M3 已经**真实发生过一次**（`meal` / `travel` 从第 4 步起就在读写
> `mealPlan` / `travelPlan` / `travelItem`，白名单却一直只有 4 个，直到第 6 步才排查出来）。
> 本期只加 **1 个** domain，反而更容易被当成小事顺手漏掉。
>
> ⚠️⚠️ **重传时务必确认 `TOMBSTONE_DOMAINS` 是 8 个值的「完整集合」，
> 而不是「只剩 `transaction`」** —— 这个数组是**替换**语义，不是追加：
> 写成 `['transaction']` 会让 diet / workout / studyPlan / studyCheckin / mealPlan /
> travelPlan / travelItem **七个 domain 的删除传播一起失效**，而且**同样零报错**。
> 改这一处之前先 `git diff` 看一眼，确认只多了一个值。
>
> 重传后其余云函数**不需要**重新部署 —— 它们引用的是同一个公共模块，内容更新后自动生效。

### 2.4 更新 `checkin_tombstones` schema（可选）

右键 `uniCloud-alipay/database/checkin_tombstones.schema.json` →「上传 DB Schema」。

本期只改了 `domain` 字段的**说明文字**（枚举由 7 个写到 8 个），
`maxLength` 未变、`required` 未变 —— 属**文档性更新**，不传也不影响功能。
传了的好处是以后在控制台看字段说明时不会误以为只有 7 个 domain。

### 2.5 建 2 条索引 ⬜

> 项目里没有 `db_init.json`，uniCloud 的 db-schema 也**不支持声明索引**，
> 所以索引只能在控制台手工建（与云函数、schema 一样属于「必须手工做」的部分）。

#### 入口

uniCloud web 控制台 →「**云数据库**」→ 左侧选中 `transactions` →「**索引管理**」标签
→「**新建索引**」。

> 最省事的打开方式：在 HBuilderX 里右键 `uniCloud-alipay` 目录 →
> 「**打开 uniCloud web 控制台**」，会自动带上当前服务空间。

#### 逐条填写参数

| 集合 | 索引名（建议） | 字段与排序 | 唯一 | 用途 |
|---|---|---|---|---|
| `transactions` | `idx_family_client` | `familyId` 升序, `clientId` 升序 | ✅ **是** | 幂等键 |
| `transactions` | `idx_family_date` | `familyId` 升序, `date` 升序 | 否 | 按月份区间拉取（最高频路径） |

#### 三个容易出错的点

1. **复合索引的字段顺序不能颠倒**：所有查询都带 `familyId`，所以它**必须放第一位**。
   顺序错了索引就用不上（查询退化成全表扫描），而且**不会报错**，很难发现。
2. **建唯一索引前，表里不能已有重复值**。`transactions` 是本期新建的空集合，
   正常不会有问题；但如果你手动插过测试数据，请先删掉重复项再建，
   否则创建会失败（报重复键）。
3. **索引建好立即生效，不需要重新上传云函数**；反过来，删掉唯一索引也不会报错，
   但会**悄悄失去幂等保护** —— 别为了「让写入先跑通」去删它。

#### 怎么确认建对了

「索引管理」列表里应当能看到 2 条，其中 `idx_family_client` 带「唯一」标记。
建完后可以顺手在「数据查询」里手动插入一条重复的 `familyId + clientId` 记录，
**预期被拒绝** —— 能拒绝就说明唯一索引真的生效了。

### 2.6 部署后自检 ⬜

**方式 A（推荐，零控制台依赖）**：打开 H5（`npm run dev:h5`）→ F12 → Console：

```js
// 账本区间拉取
uniCloud.callFunction({ name: 'ledger', data: { action: 'list', from: '2026-09-01', to: '2026-09-30' } })
  .then(r => console.log('ledger.list       ', r.result))
// ⚠️ 墓碑通路（验证 §2.3 的 checkin-shared 是否真的生效）
uniCloud.callFunction({ name: 'ledger', data: { action: 'listTombstones', since: 0 } })
  .then(r => console.log('ledger.listTombstones', r.result))
```

对照结果：

| 返回 | 含义 | 处理 |
|---|---|---|
| `{"code":0,"data":[...]}` / `{"code":0,"data":[]}` | ✅ **全链路正常** | 进入 §3 |
| `{"code":401,"msg":"登录态无效或已过期"}` | ✅ 云函数与公共模块都正常，只是无登录态 | 先登录再试 |
| `{"code":400,"msg":"尚未加入家庭"}` | ✅ 鉴权通过，账号未加入家庭 | 正常 |
| `Cannot find module 'checkin-shared'` | ❌ 公共模块缺失 | 回到 §2.3 重传 |
| 集合不存在 / `collection not exists` | ❌ schema 没传成功 | 回到 §2.1 重传 |
| `未知操作: xxx` | ⚠️ 云函数是旧版本 | 回到 §2.2 重传 |
| **`listTombstones` 返回 `{"code":0,"data":{"items":[]}}`** | ✅ 也可能只是当前没有墓碑 | 见下方「墓碑通路专项验证」 |

#### 墓碑通路专项验证（务必做一次）

上面那个空数组**不能**区分「没有墓碑」和「白名单没生效」——两者长得一模一样。
用一个**会产生墓碑的动作**来验：

1. 在账本页记一笔账，等它同步成功（换设备/重进页面能看到）；
2. 把它删掉；
3. 到控制台「云数据库」→ `checkin_tombstones` 集合查看，**应当出现一条**
   `domain: 'transaction'` 的记录，且 `date` 字段**有值**（不是空串）；
4. 再用 `listTombstones` 拉一次，应当能拿到它；
5. **换一台设备重进账本页，这笔账应当消失**（这才证明「读」那一条链路也通了）。

> 若第 3 步查不到记录 → `checkin-shared` 没传成功或传的是旧版，回到 §2.3。
> 第 5 步是**唯一**能同时验证「写」与「读」两条链路的一步，**不要跳过**。
>
> ⚠️ 顺带回归一次**老模块**的删除（如删一条饮食打卡）也应照常传播 ——
> 白名单改动是**替换**语义，若把 8 个值写漏成只剩 `transaction`，
> 老模块的删除会一起失效。这一步 30 秒，很值。

## 5. 故障排查

M2-A 清单 §7 的三节仍然适用，本期补充：

| 现象 | 排查 |
|---|---|
| 账本数据不上云，但界面一切正常 | 按 M2-A 清单 §7.3 的两步法：先看 Local Storage 有没有 `uni_id_token`，再看 `family.pendingSync.v1` 的 `attempts` 与 `lastError`。**本期新增的 domain 是 `transaction`**，标记里的 `domain` 可用来定位 |
| **删除本地成功、别的设备永远看不到删除** | ⚠️ 十有八九是 `checkin-shared` 没重传（见 §2.3）。到控制台看 `checkin_tombstones` 有没有 `transaction` 记录 —— 没有就是白名单没生效 |
| **老模块（饮食 / 运动 / 学习 / 食谱 / 出行）的删除忽然也不传播了** | 白名单被写漏了：`TOMBSTONE_DOMAINS` 应是 **8 个值的完整集合**，不是只含 `transaction`。回 §2.3 重传 |
| `Cannot find module 'checkin-shared'` | 公共模块没传成功，重传 §2.3 |
| `未知操作: xxx` | 云函数是旧版本，重新上传部署 §2.2 |
| **月汇总数字偏小 / 只统计了当天** | 拉取通路写成了「按单日」。账本必须走 `pullTransactions(from, to)` 的**日期区间**（方案 §3.4）—— 只拉当天会让月汇总基于残缺数据求和 |
| 切到某个月后那一整月的记录都不见了 | 同上；另外检查回写是否**按 `date` 分桶逐桶写**（整段覆盖会把某一天的记录抹掉） |
| 编辑一笔旧账时报「保存失败」 | 检查是否用了旧版前端：编辑态必须**禁用日期选择器**。`date` 是本机分区键与云端拉取维度，改了会让记录在新分区里找不到（方案 §3.6 第 1 条） |
| 导入报「成功 N 条」但 B 端少了一部分 | 本机读取阶段就可能丢数据（`parseStoredArray` 把校验不通过的条目**既不返回也不报错**地滤掉）。以「本机实际能读出的条数」为基准核对，并把 `fixes` / `invalid` 摊开看；真正的漏项应走 `invalid` **显性报出来**，而不是被悄悄丢掉 |
| 导入期间页面像卡死了 | 是体验问题不是数据问题（导入幂等，重复点不会坏数据）。检查进度回调是否每完成一条就更新 |
| 同一笔账被云端建了两条 | 唯一索引 `idx_family_client` 没建成功（幂等键失效）。回到 §2.5 |

## 6. 回滚

| 场景 | 处理 |
|---|---|
| 前端有问题 | 回退到上一个提交并重新构建；**云端数据不受影响** |

| 需要彻底回退 | 删除 `transactions` 集合；前端回退代码 |

> ⚠️ 本期**有一处跨期影响**：`checkin-shared` 的 `TOMBSTONE_DOMAINS` 被 7 → 8。
> 回退公共模块会让 `transaction` 的墓碑读写一起失效
> （表现为「账本的删除不再传播」），但**已经写下的老墓碑仍在库里**、
> 老模块（diet / workout / study / mealPlan / travelPlan / travelItem）完全不受影响。
>
> 除此之外**没有破坏性变更**：`diets` / `workouts` / `study_plans` /
> `study_checkins` / `favorite_foods` / `meal_plans` / `travels` / `travel_items` /
> `families` / `family_members` / `uni-id-users` / `checkin_tombstones` 的
> schema 均未做**功能性**改动（`checkin_tombstones` 只改了字段说明文字）。
>
> ⚠️ 老数据导入是**只写不删**的操作，回滚前端不会把已导入云端的记录撤回来；
> 若确实要清空，需要在控制台按 `familyId` 逐集合删除（**谨慎操作**）。
