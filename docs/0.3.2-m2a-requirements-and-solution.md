## 1. 范围与验收标准

### 1.1 本期范围（M2-A）

| 模块 | 内容 |

### 1.2 出口验收标准

## 2. 需求确认结论

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 云函数拆分 | **拆成 `diet` + `workout` 两个云函数**，沿用 `family`/`member` 的「一模块一函数」惯例 |
| 2 | 运动数据模型 | **扩展支持有氧**（在组明细之外增加时长 / 距离 / 卡路里） |
| 3 | 饮食数据模型 | 沿用现有字段，**额外增加「常用食物」快捷选择** |
| 4 | 离线能力 | **轻量版**：本地优先 + 待同步标记 + 下次进入页面重试 |
| 5 | 历史数据读法（补充约定） | **云端为准、本地兜底**；老数据不主动上云 |

### 2.1 关于「拆分云函数」的说明

需要澄清一点：**集合（存储）从来不是合并的对象**。合的是「云函数」这个 API 入口。无论哪种方案，
`diets` 与 `workouts` 都是两个独立集合，字段、校验、权限各管各的——「运动与饮食做两方面存储」的
初衷在任何方案下都成立。

选择拆分的理由：

1. **校验逻辑差异大**——饮食是平面字段，运动是嵌套结构（`sets`）+ 有氧字段，合并后函数内会有两套
   完全不同的字段白名单，靠 `type` 分流；
2. **改一处、动全身**——改饮食要重新上传含运动逻辑的整个函数；
3. **无法独立回滚**——运动出问题回滚会连带饮食；
4. **日志混杂**——排查需按 `type` 过滤。

> 早前「合并更省部署」的理由不成立：文档 §5.3 已说明可在 `cloudfunctions` 目录右键
> 「上传所有云函数、公共模块及 actions」一次批量上传，部署成本差异基本为零。

### 2.2 关于「离线能力轻量版」的说明

| 维度 | 轻量版（本期） | 完整版（路线图 §9/§10） |
|---|---|---|
| 失败后 | 记「待同步」标记 | 进持久化队列（含重试次数、下次重试时间） |
| 重试触发 | 进页面 / App 回前台 | 上述时机 + 网络恢复自动触发 + 定时器 |
| 退避 | 无，每次全量重试 | 指数退避 1s→2s→4s→… |
| 顺序 | 不保证 | 按入队顺序重放 |
| 可观测 | 控制台日志 | 「待同步 N 条」UI |
| 额外代码 | 约 1 个文件 | SyncQueue + SyncService + 网络监听 + 状态 UI |

选轻量版的理由：

1. **覆盖真实场景的九成**——家庭打卡的断网场景很具体（白天在外网络差时打卡，晚上回家连 WiFi
   打开小程序），「下次进页面重试」正好命中；
2. **本机无法端到端验证云链路**——指数退避、网络监听、队列乱序重放恰恰是最难被 mock 覆盖、
   最容易藏 bug 的部分，先不引入；
3. **做成可替换接口**——同步逻辑全部收在 `CheckinSyncService` 后面，将来升级只换实现，
   页面与 store 不用动。

### 3.4 `favorite_foods` 集合（常用食物）

```jsonc

  "_id": "服务端主键",
  "familyId": "家庭归属",
  "name": "牛奶",                     // 家族内唯一（familyId + name）
  "quantity": "1 杯",
  "calories": 150,
  "protein": 8,
  "carbs": 12,
  "fat": 5,
  "useCount": 7,                     // 使用次数，用于排序
  "lastUsedAt": 1757000000000,
  "createdByUid": "首次录入者 uid",
  "createdAt": 1757000000000,
  "updatedAt": 1757000000000
}
```

**收集策略（默认行为，可调整）**：**自动收集 + 手动删除**。

- 每次 `diet.add` 成功后，服务端按 `familyId + name` upsert 一条常用食物：
  已存在则 `useCount += 1`、刷新营养值与 `lastUsedAt`；不存在则新建；
- 列表按 `useCount desc, lastUsedAt desc` 排序，默认取前 20；
- 提供删除入口，用户可清掉不想要的。

这样用户不需要额外做「收藏」动作，常用食物会自然沉淀。

## 4. 云函数设计

### 4.1 公共模块 `common/checkin-shared`

两个函数共用鉴权与家庭归属推导，避免复制（鉴权逻辑复制是安全风险）。

```js
// uniCloud-alipay/cloudfunctions/common/checkin-shared/index.js
const db = uniCloud.database()

// 校验登录态 → { code:0, uid } 或 { code:401, msg }
exports.getUid = async (context, event) => { ... }

// 读 uni-id-users 推导家庭 → { code:0, familyId, role } 或 { code:400, msg }
exports.getFamily = async (uid) => { ... }

// 合并：一次调用拿到 uid + familyId，失败直接返回错误对象
exports.resolveContext = async (context, event) => { ... }
```

两个云函数的 `package.json` 增加依赖：

```json
{
  "name": "diet",
  "version": "1.0.0",
  "main": "index.js",
  "dependencies": {
    "uni-id-common": "file:../common/uni-id-common",
    "checkin-shared": "file:../common/checkin-shared"
  }
}
```

### 4.2 `diet` 云函数

`exports.main(event, context)` → `resolveContext` → 按 `event.action` 路由：

| action | 入参 | 返回 | 说明 |
|---|---|---|---|
| `list` | `date` 或 `from`+`to` | `{code:0, data:[...]}` | 按 `familyId + date` 查询 |
| `add` | `clientId, date, mealType, foodName, quantity, calories?, protein?, carbs?, fat?, memberId?` | `{code:0, data:{_id}}` | **clientId 幂等**：已存在直接返回既有 `_id` |
| `update` | `clientId` + 待改字段 | `{code:0}` | 先校验归属 |
| `remove` | `clientId` | `{code:0}` | 先校验归属 |
| `listFoods` | `keyword?` `limit?` | `{code:0, data:[...]}` | 常用食物列表 |
| `removeFood` | `name` | `{code:0}` | 删除常用食物 |

### 4.3 `workout` 云函数

| action | 入参 | 返回 |
|---|---|---|
| `list` | `date` 或 `from`+`to` | `{code:0, data:[...]}` |
| `add` | `clientId, date, category, exerciseName, sets, durationMin?, distanceKm?, calories?, memberId?` | `{code:0, data:{_id}}` |
| `update` | `clientId` + 待改字段 | `{code:0}` |
| `remove` | `clientId` | `{code:0}` |

### 4.4 安全规则（两个函数共用）

1. **`familyId` 一律由服务端从 token 推导**，**忽略客户端传入的 familyId**（防越权）；
2. `update` 必须先按 `familyId + clientId` 查回记录，**查不到返回 404**——
   杜绝用别人的 `clientId` 跨家庭操作；
3. `remove` **刻意做成幂等**：记录不存在时同样返回成功（`{ removed: false }`）。
   原因见下方说明；
4. `memberId` 非空时校验该成员属于本家庭（查 `family_members`），不合法则置 `null`，
   防止跨家庭串数据；
5. `clientId` 必填、`string`、长度 ≤ 64；`date` 必须匹配 `^\d{4}-\d{2}-\d{2}$`；
6. 集合 `permission` 全 `false`，客户端无法直连数据库。

> **为什么 `remove` 要和 `update` 区别对待？**
> 离线队列重投一条「已经删成功」的记录时，若返回 404，前端会把它当成失败而**无限重试**，
> 永远出不了队。而「记录不存在」本身即等于删除的目标已达成，返回成功更符合语义。
> `update` 则不同——找不到记录说明客户端状态与服务端不一致，应该显式暴露出来。

### 4.5 幂等设计

`add` 与 `update` 均以 `familyId + clientId` 为唯一键做 upsert。这样：

- 弱网重试不会产生重复记录；
- 「待同步」队列重复投递是安全的；
- 前端可以在拿到云返回前就认为写入成功。

## 5. 前端改造

### 5.1 分层与改动面

```
页面(diet.vue / workout.vue)  ← 模板基本不动（仅表单组件内部改）
    ↓
store(diet / workout)         ← API 签名保持不变，内部改为本地优先 + 异步上云
    ↓
service(DietService / WorkoutService)  ← 完全不动（本地校验与排序逻辑复用）
    ↓
repository(本地) + remote(新)  ← 新增 remote 层
```

**保持 store 的同步 API 签名不变**是本方案的关键：`load/add/update/remove` 仍为同步返回，
页面无需改造即可继续工作。

错误文案统一走已有的 `cloudErrorText()`（兼容 `msg / message / errMsg`）。

### 5.4 读写路径

**读（已确认：云端为准、本地兜底）**

```
load(date)
  → 读本地缓存立即渲染（秒开）
  → 后台拉云端 list({date})
  → 合并：本地 ∪ 云端，同 id 以云端为准，本地独有记录保留
  → 回写本地缓存 + 刷新 UI
```

**写**

```
add/update/remove
  → 写本地缓存（UI 即时生效）
  → 记入待同步标记
  → 异步调云端
     成功 → 清除标记
     失败 → 保留标记，下次重试
```

**重试**：页面 `onShow` 与 App `onShow`（回前台）时扫描待同步标记，逐条重发；
连续失败超过 5 次则丢弃并 `console.warn`，避免死循环。

**冲突**：`last-write-wins`（服务端按 `updatedAt`），MVP 可接受。

## 6. 数据兼容

### 6.1 ⚠️ 关键兼容风险：老运动记录没有 `category`

现有运动记录**都没有 `category` 字段**。如果把它设为必填，`parseStoredArray` 在校验时会把
老记录判定为非法并**静默丢弃**——等同于用户历史训练数据消失。

**处理规则（必须有测试守住）**：

- `category` 在类型与校验层**保持可选**；
- 读取时归一化：`category ?? (sets.length > 0 ? 'strength' : 'cardio')`；
- 备份导入（`validateBackupPayload` → `validateWorkoutEntry`）走同一套容忍规则。

### 6.2 其他兼容项

| 项 | 处理 |
|---|---|
| 老记录未上云 | 读时「本地兜底」保留显示，不主动回传云端（留 M4） |
| `memberId` 引用已删除成员 | 展示层 `familyStore.nameOf()` 已有兜底 |
| 老饮食记录 | `DietEntry` 结构未变，无需处理 |

**两条关键设计**：

1. **`lib.js` 保持自包含、不跨模块 `require`。**
   云函数是独立部署单元，`require('checkin-shared')` 在本地跑测试时解析不到（`node_modules`
   要等上传时由 uniCloud 生成）；而真正需要共享的鉴权代码要碰 `uniCloud.database()`，本身
   也无法单测。因此把「纯逻辑」与「共享鉴权」彻底分开：`lib.js` 可测，`common/checkin-shared`
   只管 `index.js` 用的鉴权，不参与单测。

2. **更新走「合并 → 整体复校」，而不是逐字段打补丁。**
   `mergeXxxPatch(existing, patch)` 先合成一份完整记录，再交给同一个 `validateXxxPayload` 全量校验。
   这样即使 patch 只改了 `category`，也能识别出「切成有氧却还留着力量组明细」这类矛盾——
   逐字段校验是发现不了的。

**服务端归一化**：组明细的 `order` 一律按数组下标重排（不信任客户端顺序）；`id` 缺失时补
`set-<n>`，保证回传前端后仍满足 `WorkoutSet` 的形态要求。

**跨模块守卫已验证有效**：去掉 `toClientWorkout` 中的 `set.id` 回填后，
「toClientWorkout 的输出能被前端 validateWorkoutEntry 接受」**立即失败**——
证明若云端丢掉 `set.id`，前端 `isWorkoutSet` 会判定非法，整条记录会被静默丢弃。

| `tests/cloud-map.test.ts`（新，38 项） | 双向映射、`null` ↔ `undefined` 换算、列表过滤、源码守卫、调用行为（mock `callFunction`） |

**三条关键设计**：

1. **`null` ↔ `undefined` 的换算集中在这一层。**
   云端把「未填写」统一存 `null`，而前端 `numberError` 只放行 `undefined`——
   中间漏掉换算，云端回来的记录会被本地 Repository 静默丢弃。故下行统一 `null → undefined`。
2. **上行反过来：`undefined → null`（显式清空）。**
   `callFunction` 走 JSON 序列化，`undefined` 键会被直接丢掉；而云端 `mergeDietPatch`
   以「键缺失 = 不修改」为准。若不显式写 `null`，用户在表单里清空热量后保存，
   旧值会被云端顶回来——「清空无效」这类现象很难反查到序列化层。
3. **列表映射在前端复用同一套校验器再过滤一遍。**
   云端虽是可信来源，但记录落进本地缓存后仍要过 `parseStoredArray`；
   在这一层先过滤并 `console.warn` 计数，能把「云端数据脏」与「本地读不到」两类问题区分开。

**两处与文档初稿不同的修正**：

- `removeCloudDiet` / `removeCloudWorkout` 返回 `{ removed: boolean }` 而非 `void`：
  服务端删除是幂等的（记录不存在也返回 `code 0`），把 `removed` 透出来，
  调用方才能区分「删掉了」与「云端本来就没有」。返回类型写成 `void` 是个**不诚实的声明**，
  第一版就是这么写的，被行为测试当场抓出（`expected { removed: false } to be undefined`）。
- `addCloudXxx` 返回 `{ _id, duplicated? }`：`duplicated` 是服务端幂等命中的信号，
  离线队列重投时据此判断「这条其实早就写进去了」。

**类型层面的坑（已写进代码注释）**：`CloudDietPayload` / `CloudWorkoutPayload`
必须声明为 `type` 而不是 `interface` —— TypeScript 只为对象**类型别名**推导隐式索引签名，
而 `callXxx(action, payload: Record<string, unknown>)` 要求可索引，用 `interface` 会报 `TS2345`。

**兼容守卫已验证有效**：把 `downNumber` 改成透传 `null`（模拟「忘记换算」这一最典型错误）后，
**7 项测试立即失败**（`fromCloudDiet` / `fromCloudWorkout` 产出物不再通过前端校验、
列表过滤连合法记录一起丢掉等）。改回后 248 项全绿。

**源码守卫**：新增断言 `src/unicloud/index.ts` 中不存在裸 `uniCloud.xxx()`，
且云函数调用确实经 `getCloud().callFunction`。守卫前先剥离注释，
避免注释里对裸调用的**说明文字**被误判为真实代码（`getCloud()` 的注释里正好写了 `uniCloud.xxx()`）。
